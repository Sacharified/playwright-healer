**Gathered:** 2026-04-27

<domain>
## Phase Boundary

Phase 01.2 fixes a single, scoped runtime bug discovered during Phase 03 SC-1 live verification on 2026-04-27. The bug is pre-existing in Phase 01: `action.yml` Step 6 invokes the runtime via `npx tsx src/index.ts`, and the `npx → tsx → node` spawn chain drops every environment variable whose name contains a hyphen. Because the `INPUT_*` env block in Step 6 uses `@actions/core` v3's hyphen-preserving names (e.g., `INPUT_HEALER-TOKEN`, `INPUT_API-KEY`), every `core.getInput()` call for a kebab-cased input returns the empty string when the action runs in real CI.

What this phase delivers (and only this):

1. The composite action runtime is changed so a hyphenated `INPUT_*` env var reaches the spawned Node process intact, restoring `core.getInput()` for every kebab-cased input.
2. A regression test in `phase1-self-test.yml` asserts the chosen spawn shape preserves a hyphenated `INPUT_*` env var, isolated as a dedicated job (not piggybacked on existing scenarios).
3. Phase 03 SC-1 / SC-3 unblocked — once 01.2 ships, the Phase 03 HUMAN-UAT G-01 can be closed and SC-1 / SC-3 can be re-attempted on a fresh fork run.

Explicitly out of scope:
- Compiling TypeScript to JavaScript at build time and shipping a bundled runtime (candidate fix #2 in G-01). That is the proper Phase 6 release shape.
- Renaming `INPUT_*` env keys to underscored forms (would require touching `@actions/core` call sites and is a larger blast radius).
- Verifying every consumer of `getInput()` — the regression test on a single hyphenated var is sufficient because the bug is at the spawn layer, not the input parsing layer.

</domain>

<decisions>
## Implementation Decisions

### D-01.2-01 — Empirical validation BEFORE editing action.yml (gate)
**Locked.** The fix `./node_modules/.bin/tsx` is the *recommended* fix in G-01, not a *verified* one. The G-01 diagnostic only proved that `node` preserves hyphenated env vars and that `npx tsx` strips them. It did not test the proposed remediation. If the stripping happens inside `tsx` itself (rather than in `npx`'s resolution layer), `./node_modules/.bin/tsx` will not fix the bug. The first task in the plan MUST be a one-shot empirical check that runs the candidate spawn shape against a hyphenated env var and confirms the var survives. Only if that check exits 0 does the action.yml edit proceed. If it fails, the plan must escalate to candidate fix #2 (compile to JS) or #3 (env-var bridge) before touching action.yml.

The check shape (executor runs locally, no PR yet):
```
INPUT_FOO-BAR=hello ./node_modules/.bin/tsx -e "process.exit(process.env['INPUT_FOO-BAR']==='hello'?0:1)"
```
Exit 0 → fix is valid → proceed. Exit non-zero → escalate, do not edit.

### D-01.2-02 — Fix shape: `./node_modules/.bin/tsx` (path-resolved)
**Locked, contingent on D-01.2-01.** Replace `npx tsx` with the resolved binary path so neither `npx`'s spawn behavior nor its package-resolution layer is involved. The two call sites in `action.yml` resolve differently:
- **Step 6** runs with `working-directory: ${{ github.action_path }}` and the action's `node_modules` lives there (Step 2 ran `npm ci --production` in `${{ github.action_path }}`). Use `./node_modules/.bin/tsx src/index.ts`.
- **Step 5** has no `working-directory` (intentional — `start-command` spawns relative to consumer workspace). Use `${{ github.action_path }}/node_modules/.bin/tsx ${{ github.action_path }}/src/healer/wait-for-ready.ts`.

The `security-lint.yml` `npx tsx --eval` site is **NOT** in scope — it doesn't pass `INPUT_*` env vars and is structurally different (eval, not script invocation).

### D-01.2-03 — Step 5 in scope (consistency, not bug-fix)
**Locked.** Step 5's env block uses underscored names only (`BASE_URL`, `STARTUP_TIMEOUT_SECONDS`, `HEALER_TOKEN`, `GH_OWNER`, `GH_REPO`, `TEST_TITLE`, `TRIGGERING_RUN_URL`), so it is **not** currently affected by the hyphenated-stripping bug. Step 5 is included in the fix anyway for consistency: a single spawn convention across the action prevents a future env-block edit (e.g., adding a hyphenated var to Step 5) from silently regressing. This is the smaller blast radius of the two readings — exclude-Step-5 would need a comment explaining why one site uses one shape and the other uses another.

### D-01.2-04 — Regression test as a dedicated, isolated job
**Locked.** Add a new top-level job to `phase1-self-test.yml` whose only purpose is to assert that a hyphenated `INPUT_*` env var survives the action's chosen spawn shape. The job must NOT piggyback on an existing scenario (Scenarios 1, 4, 5 also exercise the bug indirectly, but they are testing other invariants — log masking, fail-fast, redacted summary — and have been silently failing without surfacing the env-var issue clearly). The dedicated job is the regression signal that future contributors will read when they touch the spawn line. The job's assertion uses the same shape as D-01.2-01 (set hyphenated `INPUT_FOO-BAR`, run the chosen spawn, assert the var arrives at Node).

### D-01.2-05 — Verification: re-run Sacharified phase1-self-test workflow
**Locked.** The fix is verified live by re-running `phase1-self-test.yml` (which has been failing since 2026-04-25) and observing all five scenarios pass. Local unit tests (vitest with `@actions/core` mocked) cannot catch this — they bypass the npx-tsx invocation chain entirely. The verification step in the plan must include "GitHub Actions run of phase1-self-test.yml passes all jobs" as the empirical signal.

### D-01.2-06 — No `@actions/core` source changes
**Locked.** The fix is at the action.yml spawn layer. `src/index.ts` and any consumer of `core.getInput()` remain untouched. The hyphenated `INPUT_*` naming convention is preserved because `@actions/core` v3 expects it (per Phase 01 STATE: "@actions/core v3 getInput maps hyphens to hyphens in env var name").

### Claude's Discretion
- Exact wording and YAML structure of the new self-test job (job name, scenario number, env var key chosen) are at the planner's discretion within the constraints above.
- Whether the regression-test job uses the action via `uses: ./` (with a custom command) or runs `./node_modules/.bin/tsx` inline as a shell step — both are acceptable; planner picks the simpler shape.
- Whether the empirical-validation gate (D-01.2-01) is a separate atomic task in the plan or the first behavioral assertion inside the same plan as the action.yml edit — both are acceptable as long as no edit lands without the assertion passing first.

</decisions>

<specifics>
## Specific Ideas

- The empirical-validation check from D-01.2-01 should be runnable locally (`npm ci`, then run the one-liner) so the executor can verify before touching CI. The plan must have the executor capture the exit code and command output as evidence in the plan summary.
- Path resolution differs between Step 5 and Step 6 — the planner must NOT use the same string in both. Step 6 uses `./node_modules/.bin/tsx` (relative to `working-directory`); Step 5 uses `${{ github.action_path }}/node_modules/.bin/tsx`.
- Phase 01's `01-04-PLAN.md` (composite manifest) and `01-04-SUMMARY.md` are the prior art — read them to confirm the working-directory contract before editing.
- Existing `phase1-self-test.yml` job naming convention: hyphen-separated lower-case (`self-test-masking`, `self-test-invalid-mode`, etc.). The new job should follow this (e.g., `self-test-hyphenated-input-env`).
- The regression-test job does NOT need to invoke the full `./` action — that creates noise from real-mode validation (e.g., Zod superRefine for missing api-key). A minimal job that runs `npm ci --production` and the one-liner under `${{ github.action_path }}` (or repo root, since the fix is committed there) is sufficient. Decision is the planner's.

</specifics>

<deferred>
## Deferred Ideas

- **Compile TypeScript to JavaScript at build time and ship `dist/index.js`** (G-01 candidate fix #2). Removes runtime tsx entirely; this is the proper Phase 6 release shape per project research (no runtime tsx in shipped action). Track in Phase 6.
- **Env-var bridge in a bash preamble** (G-01 candidate fix #3). Reads `/proc/self/environ` and re-exports under underscored names. Would require also patching `@actions/core` call sites. Larger blast radius than D-01.2-02; not needed unless D-01.2-01 fails.
- **Rename hyphenated inputs entirely** (e.g., `healer-token` → `healer_token` everywhere). Breaks GitHub Actions input naming convention (kebab-case is standard); rejected.

</deferred>
