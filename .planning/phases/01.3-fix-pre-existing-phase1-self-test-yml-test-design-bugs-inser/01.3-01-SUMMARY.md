## Failure Diagnosis: verify-log-mask (Job B)

**Implicated SC#:** SC#2 (Scenario 1 canary-mask test)

**Error from `--log-failed`:**

```
##[error]Canary appeared in the log — masking FAILED
--- Offending lines: ---
##[group]Run echo "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"
144:2026-04-27T21:58:37.3124577Z [36;1mecho "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"[0m
##[error]Process completed with exit code 1.
```

**Root cause:** The `run:` block in the "Pre-register canary with runner masker" step uses the command:
```yaml
run: echo "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"
```

The GitHub Actions runner logs the command text (shown as `[36;1mecho "::add-mask::..."[0m`) in the step header **before** the shell executes the echo. The `::add-mask::` workflow command is not processed until the echo outputs it to stdout. This creates an inescapable leak: the literal `test-canary-DO-NOT-USE-REAL-KEY` appears in the step header at line 144 of Job A's log, which is then found by Job B's grep.

This is a plan design bug in option (a): the RESEARCH acknowledged masking is non-retroactive, but did not account for the runner's command-echo (the `[36;1m...` ANSI-styled lines showing the command being run) appearing in the log before the command executes. The `::add-mask::` processing happens from stdout, but the command text is logged by the runner before stdout is visible.

**Attempted mitigation that won't work:**
- Using `env: CANARY: <literal>` + `run: echo "::add-mask::$CANARY"` — the `env:` block would also show `CANARY: test-canary-DO-NOT-USE-REAL-KEY` in the step header.
- Splitting the string across variables — all parts would appear in the command log.

**Viable fix options (requires user decision):**

**Option A: Accept the limitation — downgrade verify-log-mask to verify the `with:` step header masking only (not the registration step's own command).**
Modify the "Pre-register canary" step to use a form that doesn't expose the literal in the command text. Use a GitHub secret (`secrets.TEST_CANARY`) — but this breaks fresh-fork no-secrets requirement (SC#3 Pitfall 8).

**Option B: Use `continue-on-error: true` on the `Pre-register` step, or use a different registration mechanism.**
The `::add-mask::` approach is structurally limited when the value is a literal in the run: command.

**Option C: Restructure the test to not grep for the registration step's command text.**
Since line 144 (the command echo) is unambiguously the runner echoing the command — not the canary leaking from `with:` or from the action body — the test could use a stricter grep that excludes the `::add-mask::` setup step's own log group. For example: check that the canary does NOT appear in the `Invoke action` step's log lines, rather than the entire Job A log.

**Option D: Remove verify-log-mask entirely (accept Scenario 4 as the masking proof).**
Scenario 4 already verifies that the redacted markdown output does NOT contain the canary (the `core.setSecret`-driven redaction in the markdown table). The verify-log-mask job tests the runner masker — a different but overlapping concern. With SC#1 fixed, Scenario 4 provides adequate coverage of the masking contract.

**Recommendation (for user decision):** Option C or Option D. Option C is the most surgical: instead of grepping the entire Job A log, grep only the lines from the "Invoke action" step (the step that runs `uses: ./`), which is the step that would leak the canary if masking failed. The registration step's command echo containing the literal is expected and harmless. This requires fetching the log and filtering by step group, which is more complex but preserves the test's intent.

## Plan Correction (post-checkpoint)

User chose **Option C** in response to the verify-log-mask failure: filter `::add-mask::` lines from Job B's grep haystack before checking for canary leak, preserving Phase 01-06's TWO-JOB pattern (Pitfall 9 / Pattern 13) while removing only the self-referential noise from the registration step's command echo.

### Behavior gap RESEARCH §Pattern 4 missed

The RESEARCH correctly captured that masking is non-retroactive (the `::add-mask::` and `core.setSecret()` registration applies only to log lines emitted AFTER registration). What it missed is a related but distinct timing fact: **the GitHub Actions runner echoes every `run:` block's command text in the step header — the `[36;1m...[0m` ANSI-styled display lines starting with `Run …` — BEFORE the shell executes the command and BEFORE stdout/stderr emissions can engage the masker.**

Concretely: the step
```yaml
- name: Pre-register canary with runner masker
  shell: bash
  run: echo "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"
```

produces in Job A's log (observed line 144):
```
##[group]Run echo "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"
[36;1mecho "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"[0m
```

The runner displays the `run:` script content in the step header. The shell has not yet executed the echo, so the `::add-mask::` workflow command has not yet been emitted to stdout, so the runner's mask filter has not yet been told about the literal. The literal therefore appears in the log on the registration step's own command-echo line.

This is structurally inescapable for any `echo "::add-mask::LITERAL"` shape: the literal MUST appear in the `run:` command text for the echo to register it, and the runner MUST display the `run:` command text before executing it. Workarounds via env-var indirection (`env: CANARY: <literal>`) don't help — the runner also displays env-block values in the step header.

### Why Option C over Option D

Option D (remove `verify-log-mask` entirely, rely on Scenario 4's redacted-markdown grep) would have lost the TWO-JOB log-grep pattern — an architectural invariant established in Phase 01-06 (Pitfall 9 / Pattern 13: in-job log-grep races log API finalization, so a separate `needs:` + `if: always()` job is mandatory for log-based assertions). Phase 01-06 spent budget on this design; abandoning it would erode prior work.

Option C is a one-line surgical edit to Job B's haystack: `grep -v '::add-mask::' job-a.log > job-a-filtered.log` before the canary grep. The exclusion is well-bounded — by construction, lines containing `::add-mask::` necessarily contain the registered literal (that's the registration mechanism). Filtering those lines removes only the self-referential noise; ANY other leak (the `with:` step header on `uses: ./`, an `INPUT_API-KEY:` env-block dump, action body output) appears on a non-`::add-mask::` line and still trips the gate.

### What the test still does and does not verify with the filter

**Verifies (preserved):**
- The runner masker correctly redacts the canary in the action's `with:` step header (the original Phase 01-06 contract).
- Any leak from `INPUT_*` env-block dumps in the spawned step's environment display.
- Any leak from the action body's stdout/stderr (dispatcher logs, errors, summary writes).
- Any leak from intermediate composite-action steps before Step 6.

**Does NOT verify (acknowledged):**
- That `src/index.ts` calls `core.setSecret()` correctly — that contract is verified by Scenario 4's redacted-markdown grep (the `core.setSecret`-driven redaction in the dry-run output).
- That the `::add-mask::` registration step itself does not leak the literal in its own command echo — the filter explicitly excludes those lines because they would always contain the literal by design.

The trade-off is identical to the original SC#2 option (a) trade-off documented in the plan: this test verifies the runner masker's effective behavior, not the dispatcher's setSecret contract. The filter just acknowledges a previously-uncaptured timing fact about how the runner displays `run:` block contents.
