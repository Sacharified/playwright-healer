# Phase 01.3: Code Review Report

**Reviewed:** 2026-04-27

## Summary

Phase 01.3 stitches the dispatcher's dry-run markdown summary to a composite-action output (`dry-run-summary`) so phase1-self-test Scenarios 4+5 can read the redacted markdown table cross-step instead of relying on the per-step-scoped `$GITHUB_STEP_SUMMARY`. The change is small (1 line in `src/index.ts`, 12 lines in `action.yml`, plus workflow plumbing and two new vitest files) and the live CI run 25022284855 was green on all 7 jobs.

The most important review concern was T-01.3-01 (information disclosure via the new output). It is fully mitigated:

- `setSecret × 3` (src/index.ts:42-44) registers the three secret values with the runner mask **before** any log line, output, or summary write.
- `runDryRun()` constructs the markdown from cell strings that are either hardcoded redactions (`'(set — redacted)'` for healer-token / github-token at lines 146-147) or three-way conditional placeholders for api-key (`'(set — redacted)' | '(empty — allowed for ollama)' | '(empty)'` at lines 125-127). No raw-secret interpolation path exists in the markdown.
- `core.setOutput('dryRunSummary', md)` (src/index.ts:158) thus receives a string that, by construction, cannot contain a raw secret value. Even if it did, the runner's setSecret mask would redact on emission (defense-in-depth, belt-and-suspenders).

The four invariant strings (`dryRunSummary` camelCase, `dry-run-summary` kebab, `run-playwright-healer` slug, canary literal) appear with consistent counts and no typos across `src/index.ts`, `action.yml`, the workflow, and both vitest files. The action.yml-structure test enforces this consistency at CI time (RESEARCH Pitfall 2 silent-failure-mode guard), which is the right defense.

YAML structure in `action.yml` is correct: `outputs:` is a top-level sibling of `inputs:` and `runs:`, not nested inside `runs.steps`. Indentation is 2-space and consistent. The `${{ steps.run.outputs.dry-run-summary }}` reference in Scenarios 4+5 is safely env-indirected via `env: SUMMARY:` blocks (Pitfall 1 — Markdown content with backticks/pipes is treated as data, not shell tokens).

The `verify-log-mask` Job B `grep -v '::add-mask::'` filter (line 96) correctly suppresses the registration step's own command echo (which by construction contains the literal canary because `::add-mask::` IS the registration mechanism). Any genuine leak from the `with:` step header or the action body would still trip the gate on a non-`::add-mask::` line.

Findings below are documentation drift and minor consistency observations, not correctness issues.

## Info

### IN-01: runDryRun JSDoc no longer fully describes the function's effects

**File:** `src/index.ts:118-123`
**Issue:** The JSDoc above `runDryRun` still says the function "writes a redacted config summary to $GITHUB_STEP_SUMMARY and exits 0". As of this phase, `runDryRun` ALSO publishes the same redacted markdown to a composite-action output via `core.setOutput('dryRunSummary', md)` (line 158), and that emission is load-bearing for phase1-self-test Scenarios 4+5 — it is not incidental. A future reader looking only at the JSDoc will not realise the setOutput call is part of the function's contract and may delete it as "redundant with summary.write()".
**Fix:** Update the JSDoc to mention both sinks and call out that the setOutput emission is the public composite-action `dry-run-summary` output (with a forward-pointer to the action.yml `outputs.dry-run-summary` block).

```ts
/**
 * Dry-run: write a redacted config summary to TWO sinks and exit 0.
 *
 *   1. $GITHUB_STEP_SUMMARY (human-visible run summary), via core.summary.addRaw → write.
 *   2. The composite-action output `dry-run-summary` (machine-readable across
 *      step boundaries), via core.setOutput('dryRunSummary', md). The TS key is
 *      camelCase; action.yml `outputs.dry-run-summary.value` translates it back
 *      to kebab for the consumer-facing API. Phase1-self-test Scenarios 4+5
 *      depend on this output — do not remove without updating those scenarios.
 *
 * Per D-05, the three secrets are NEVER emitted (omitted rather than replaced
 * with ***, because the runner mask would replace them anyway — belt and
 * suspenders). This is the permanent dry-run contract: exit 0 + no side effects.
 */
```

### IN-02: Test description claims "(anthropic + canary key)" but does not assert canary behavior

**File:** `tests/unit/dispatcher-dry-run.test.ts:84`
**Issue:** The first test's description is `'calls core.setOutput exactly once with key dryRunSummary (anthropic + canary key)'`, but the assertions only check the call count and the first argument; nothing verifies that the canary value (`test-canary-DO-NOT-USE-REAL-KEY`) is handled correctly. The canary-redaction assertion is in test 3 (line 121: `expect(md).not.toContain('test-canary-DO-NOT-USE-REAL-KEY')`). The suite as a whole is correct, but the test name and its assertions are out of alignment, which can mislead a reader who skims test names looking for the canary contract.
**Fix:** Either drop the `(anthropic + canary key)` qualifier from the description (since the test does not assert anything canary-specific) — e.g. `'calls core.setOutput exactly once with key dryRunSummary'` — or add a `expect(md).not.toContain('test-canary-DO-NOT-USE-REAL-KEY')` assertion to this test so the description matches behavior. The first option is the smaller change.

### IN-03: Outcome checks in phase1-self-test use raw template interpolation rather than env-indirection

**File:** `.github/workflows/phase1-self-test.yml:132, 167, 209, 266`
**Issue:** Scenarios 2/3/4/5 each test `if [ "${{ steps.run.outcome }}" != "success/failure" ]` by direct template interpolation into the shell. The phase otherwise uses the env-indirection pattern (`env: SUMMARY: ${{ ... }}` at lines 206, 263) as the workflow-injection defense. `steps.<id>.outcome` is a closed enum (`success | failure | cancelled | skipped`) controlled by the runner, so direct interpolation is practically safe — there is no plausible attacker-controlled path into that value. This is purely a consistency observation: applying the same pattern uniformly makes the safety property local rather than requiring the reader to know the enum's provenance.
**Fix:** Optional. If you want pattern uniformity, switch each outcome check to env-indirection:

```yaml
- name: Assert the invocation failed (exit code 1)
  shell: bash
  env:
    OUTCOME: ${{ steps.run.outcome }}
  run: |
    set -euo pipefail
    if [ "$OUTCOME" != "failure" ]; then
      echo "::error::Expected failure for mode=banana, got outcome=$OUTCOME"
      exit 1
    fi
    echo "OK: invalid mode produced failure outcome"
```

Recommendation: deferrable. The current code is safe and was green on CI run 25022284855; this is a style-consistency note for a future cleanup pass, not a blocker.
