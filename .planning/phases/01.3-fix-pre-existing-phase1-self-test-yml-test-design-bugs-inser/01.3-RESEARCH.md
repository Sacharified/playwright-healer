No new threat surface, no test-only flags, no behaviour change for production users — the dispatcher continues to write its summary to `core.summary` exactly as before; the new output is a parallel, self-redacted publication of the same markdown so an in-job assertion step can read it without depending on `$GITHUB_STEP_SUMMARY`'s per-step semantics.

**Primary recommendation:** Fix Scenarios 4 + 5 by switching from `$GITHUB_STEP_SUMMARY` to a composite-action output (`steps.run.outputs.dry-run-summary`), declared at action.yml top-level mapping the inner step's `core.setOutput('dryRunSummary', md)`. ### Pattern 1: Composite-Action Output Surfacing (Q3 — primary-source verified)

**What:** GitHub Actions composite actions do NOT automatically expose inner-step `core.setOutput` calls to the parent workflow. The action.yml MUST declare a top-level `outputs:` block with each output's `value:` set to `${{ steps.<inner-id>.outputs.<inner-key> }}`. Without this declaration, `${{ steps.<step-using-action>.outputs.<key> }}` in the consuming workflow is empty.

**When to use:** Every time a composite action needs to publish a value back to the consuming workflow.

**Example:**
```yaml
# Source: GitHub docs — Metadata syntax for GitHub Actions §composite outputs
# https://docs.github.com/en/actions/sharing-automations/creating-actions/metadata-syntax-for-github-actions
outputs:
  random-number:
    description: "Random number"
    value: ${{ steps.random-number-generator.outputs.random-id }}
runs:
  using: "composite"
  steps:
    - id: random-number-generator
      run: echo "random-id=$(echo $RANDOM)" >> $GITHUB_OUTPUT
      shell: bash
```

**Applied to this phase (action.yml patch):**
```yaml
# action.yml — add at TOP LEVEL, between `inputs:` and `runs:`:
outputs:
  dry-run-summary:
    description: 'Rendered redacted dry-run markdown summary (mode=dry-run only). Empty for ingest/heal modes. Self-redacted via core.setSecret — safe to log.'
    value: ${{ steps.run-playwright-healer.outputs.dryRunSummary }}

runs:
  using: composite
  steps:
    # ... existing Steps 1-5 unchanged ...

    # Step 6 (existing) — must add `id: run-playwright-healer`
    - name: Run playwright-healer
      id: run-playwright-healer    # ← ADD THIS LINE
      shell: bash
      working-directory: ${{ github.action_path }}
      env:
        # ... unchanged ...
      run: ./node_modules/.bin/tsx src/index.ts
```

**Critical detail:** The output key in `core.setOutput('dryRunSummary', md)` (camelCase) is what shows up under `steps.<id>.outputs.dryRunSummary` *inside the action.yml's value-expression*. The action-level output name (`dry-run-summary`, kebab-case) is what the consuming workflow sees. These are independently chosen — kebab-case at the action surface, camelCase inside the dispatcher follows existing project convention.

### Pattern 2: Multiline Output via GITHUB_OUTPUT Delimiter Protocol (Q1 — primary-source verified)

**What:** `@actions/core.setOutput` writes to the `GITHUB_OUTPUT` env-file using the heredoc-style delimiter protocol. The delimiter is generated as `ghadelimiter_${crypto.randomUUID()}`. The protocol is:

```
KEY<<DELIMITER
value (any number of lines, including blanks)
DELIMITER
```

The implementation throws if the key or value contains the delimiter string (collision avoidance — but since UUIDs are 128-bit random, collision is statistically impossible).

**Source:** `actions/toolkit/packages/core/src/file-command.ts` `prepareKeyValueMessage` — verified via WebFetch 2026-04-27.

**Size limits:** None enforced by `@actions/core`. The `GITHUB_OUTPUT` file itself has no documented hard cap, though the runner has a per-job total environment-file size cap (historically ~50 MB across `GITHUB_ENV`/`GITHUB_OUTPUT`). The dry-run markdown is ~30–40 lines (~2–3 KB); orders of magnitude under any plausible cap.

**Applied to this phase (src/index.ts patch):**
```typescript
// src/index.ts — runDryRun (current line 157):
//   await core.summary.addRaw(md).write();
// CHANGE TO:
await core.summary.addRaw(md).write();
core.setOutput('dryRunSummary', md);  // NEW — Phase 01.3 SC#1
```

The `setOutput` call is unconditional (no `if (process.env.CI)` gate) per SC#4 (no test-only branches). It is opt-in for production users in the sense that consumers who don't reference `steps.<id>.outputs.dry-run-summary` simply don't see it — the value is written to a per-step file the runner discards if no parent step reads it.

### Pattern 3: Per-Step `$GITHUB_STEP_SUMMARY` Semantics (Q7 — primary-source verified)

**What:** Each step in a job gets its OWN `$GITHUB_STEP_SUMMARY` file. Steps DO NOT share a file. At job completion, the runner concatenates each step's summary file into the human-visible Summary tab — but at runtime, step N+1's `$GITHUB_STEP_SUMMARY` env var points to a different (empty) file than step N wrote to.

**Source:** GitHub docs — Workflow commands for GitHub Actions: *"GITHUB_STEP_SUMMARY is unique for each step in a job. When a job finishes, the summaries for all steps in a job are grouped together into a single job summary."*

**Why this matters:** The current Scenarios 4 + 5 assertions read `$GITHUB_STEP_SUMMARY` from a step that runs AFTER `uses: ./`. That env var resolves to a fresh empty file in the assertion step's context — the dispatcher's writes are in a different file (which the runner has already finalized, but the assertion step has no path to it).

The original 01-06-SUMMARY's "Decisions Made" item #3 ("Scenario 4 hard-fails on empty summary — runDryRun always writes summary unconditionally; empty file is a regression indicator") was based on the incorrect assumption that the file is shared. It is not. The `[ -s "$GITHUB_STEP_SUMMARY" ]` check is a tautological always-empty-from-the-reader's-perspective probe. It produced apparent green only because Job A failed Zod validation early on darwin-incompatible mocks, and the assertion step never ran. With Phase 01.2's fix, Job A succeeds, the assertion step runs, and finds the empty file.

### Pattern 4: Non-Retroactive Masking + Step-Header Emission (Q4 + Q5 — primary-source verified)

**What:** `::add-mask::` and `core.setSecret()` register a value with the runner's mask filter. The mask is applied to log lines emitted **AFTER** registration. It cannot retroactively mask values already in the log buffer.

**Source 1 (non-retroactive):** Aaron Powell, "Working with add-mask and GitHub Actions" (2022): *"masking will only be applied to log messages after it is used, so you need to ensure it's used as early as possible, relative to the usage of the value you wish to mask."* Confirmed by `actions/runner` issues #475, #643, #2075 (all GitHub-staff-acknowledged behaviour).

**Source 2 (step-header emission timing):** GitHub Actions runner emits the `with:` block as part of the step header (the collapsed-by-default lines starting with `Run …` and showing input values). This emission happens BEFORE the inner step body runs — empirical confirmation in this project's own `01-06-SUMMARY` and `01.2-SUMMARY` ("Scope clarification" item 2): *"the runner emits `with: api-key: <canary>` (line 150) and `INPUT_API-KEY: <canary>` (line 205) in the step header BEFORE the action body's `core.setSecret()` runs."*

**Implication for Scenario 1:** The current TWO-JOB pattern's assertion ("canary string does NOT appear in Job A's log") is structurally impossible to satisfy when the canary is a literal value in `with:`. The runner emits the `with:` block at step dispatch — there is no log line in scope earlier than that for `core.setSecret` to run before. SC#2's two options resolve this differently:

**Option (a) — `::add-mask::` setup step BEFORE `uses: ./`:**
```yaml
self-test-masking:
  steps:
    - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd
      with:
        persist-credentials: false

    # NEW — register canary with runner masker BEFORE the action's step header is emitted
    - name: Pre-register canary with runner masker
      shell: bash
      run: echo "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"

    - name: Invoke action with dry-run and inline canary API key
      uses: ./
      with:
        mode: dry-run
        provider: anthropic
        api-key: 'test-canary-DO-NOT-USE-REAL-KEY'
        healer-token: 'test-canary-healer-token'
        github-token: ${{ github.token }}
```

**What this verifies:** The runner masker correctly masks the canary in the `with:` step header AND in any log lines emitted by the action body. This is the actually-effective masking control for `with:` values on real CI (since by step-header emission time, the action body has not yet had a chance to run any code).

**What this does NOT verify:** That the action body calls `core.setSecret()` correctly. The runner masker is already engaged from the setup step.

**Option (b) — drop literal canary in `with:`, action emits a post-setSecret canary marker:**
This requires the dispatcher to write a known marker line containing a canary-derivative AFTER `core.setSecret()` registers it. The Job B grep then asserts neither the literal canary nor any pre-mask leak appears in the log. This proves the dispatcher's masking contract end-to-end.

**Why option (b) has hidden cost:** It requires the dispatcher to emit a value after setSecret on EVERY production run (not just tests). In production, the value is the real api-key — the runner masks it to `***` so it does not leak, but the action is now writing a log line containing the redacted secret that no production user asked for. SC#4 explicitly rules out test-only branches/flags, so we cannot gate this behind `if (canary === 'test-canary-...')`. The behaviour change is therefore real: every production run grows by one log line.

**Recommendation:** **Option (a).** It verifies the runner masker (the actually-effective control for `with:` values) without imposing a production behaviour change. The setSecret contract is verified separately and adequately by Scenario 4's defense-in-depth grep ("canary absent from dispatcher-emitted summary"), which already exercises the `core.setSecret` path through the markdown table redaction.

The trade-off comment SC#2 requires is: *"This test asserts the runner masker correctly masks the canary in the step header and downstream logs. It does NOT directly verify `core.setSecret()` — that contract is verified by Scenario 4's redacted-markdown grep."*

#### Plan-Correction Note (added post-execution 2026-04-27)

This Pattern 4 description correctly captured non-retroactive masking and step-header `with:` block emission, but missed a related timing fact that surfaced during the live-CI gate of plan 01.3-01: **the runner echoes every `run:` block's command text in the step header — the `[36;1m...[0m` ANSI-styled display lines starting with `Run …` — BEFORE the shell executes the command and BEFORE stdout/stderr emissions can engage the masker.**

Concrete observation from run 25021785350, Job A line 144:
```
##[group]Run echo "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"
[36;1mecho "::add-mask::test-canary-DO-NOT-USE-REAL-KEY"[0m
```

The runner displays the `run:` script content in the step header before invoking bash. The shell has not yet executed the echo; the `::add-mask::` workflow command has not yet been emitted to stdout; the runner's mask filter has not yet been told about the literal. The literal therefore appears in the log on the registration step's own command-echo line.

**Implication for option (a):** `echo "::add-mask::LITERAL"` necessarily exposes LITERAL in the step header before masking takes effect. Workarounds via env-var indirection (`env: CANARY: <literal>`) don't help — the runner also displays env-block values in the step header. The `::add-mask::` registration still works correctly for the subsequent `uses: ./` step (the `with:` step header on the action invocation IS masked), but the registration step's own command echo is an inescapable exposure.

**Resolution applied:** Filter `::add-mask::` lines from Job B's grep haystack: `grep -v '::add-mask::' job-a.log > job-a-filtered.log` before the canary check. The exclusion is well-bounded — by construction, lines containing `::add-mask::` necessarily contain the registered literal. Any leak from non-registration sources (the `with:` step header on `uses: ./`, an `INPUT_API-KEY:` env-block dump, action body output) appears on a non-`::add-mask::` line and still trips the gate.

This preserves Phase 01-06's TWO-JOB pattern (Pitfall 9 / Pattern 13) — the alternative (remove `verify-log-mask` entirely) would have abandoned an architectural invariant established in a prior phase.

### Anti-Patterns to Avoid

- **Sharing `$GITHUB_STEP_SUMMARY` across steps:** Confirmed broken by Q7. Do not reach for it as a cross-step IPC channel.
- **Test-only branches in production code:** SC#4 forbids. Do not add `HEALER_TEST_MODE`, `if (process.env.CI === 'test')`, or `if (provider === 'anthropic' && apiKey === 'test-canary-...')` paths.
- **Calling `core.setSecret('')` conditionally:** Phase 01.1 already established that `setSecret('')` is a documented no-op and the unconditional call preserves the branchless D-07 ordering. Do not regress this.
- **Adding outputs to action.yml without an `id:` on the inner step:** The `value:` expression `${{ steps.<id>.outputs.<key> }}` requires the inner step to have an `id:`. The current Step 6 has no `id:` — that's why this phase needs to add `id: run-playwright-healer` (or similar; the planner can pick the slug).
- **Using `core.summary.write({ overwrite: true })`:** Existing call uses default (append). No reason to change.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Multiline value in `GITHUB_OUTPUT` | Manual heredoc echo with hand-picked delimiter | `core.setOutput` from `@actions/core` v3 | The toolkit picks a UUID-based delimiter and validates against collision; manual heredocs risk delimiter collision with markdown content (e.g., a row containing `EOF`) |
| Cross-step value passing | Reading `$GITHUB_STEP_SUMMARY` from a sibling step | Composite-action `outputs:` declaration | `$GITHUB_STEP_SUMMARY` is per-step (Q7); the composite-output pattern is the documented mechanism |
| Canary masking | `core.setSecret()` after the value already appeared in `with:` headers | `::add-mask::` setup step before `uses: ./` | Masking is non-retroactive (Q4); registration must precede the log line that would emit the secret |

**Key insight:** The runner masker and the composite-action output protocol are both documented, well-supported GitHub Actions primitives. The bugs in the current self-test predate this knowledge — fixing them is a matter of switching to the documented primitives, not building anything new.

## Common Pitfalls

### Pitfall 1: `core.setOutput` value mistakenly interpolated through GitHub expressions

**What goes wrong:** Workflow author writes `${{ steps.run.outputs.dry-run-summary }}` directly into a `run:` block: `run: echo "${{ steps.run.outputs.dry-run-summary }}" | grep ...`. The markdown contains backticks and pipes — when interpolated into the bash heredoc unescaped, GitHub Actions' template-engine pre-runtime substitution can produce shell syntax errors or YAML parse errors.

**Why it happens:** GitHub Actions does template-engine substitution BEFORE the shell sees the line. Backticks (`` ` ``) in the markdown become command substitution; pipes (`|`) and ampersands (`&`) become shell control chars.

**How to avoid:** Pass the output through `env:` (same workflow-runner protection as INPUT_*) and read via `$VAR` from bash:
```yaml
- name: Assert summary contents
  shell: bash
  env:
    SUMMARY: ${{ steps.run.outputs.dry-run-summary }}
  run: |
    set -euo pipefail
    echo "$SUMMARY" | grep -q '| `provider` | anthropic |' || (echo "::error::missing provider row" && exit 1)
```

**Warning signs:** "syntax error near unexpected token" in the bash log, or YAML parse failures referencing the assertion step.

### Pitfall 2: action.yml output's `value:` expression fails silently if step `id` is missing or wrong

**What goes wrong:** Author adds `outputs.dry-run-summary.value: ${{ steps.run-playwright-healer.outputs.dryRunSummary }}` but Step 6 doesn't have `id: run-playwright-healer`. The expression resolves to empty string. The composite-action output is empty. Scenarios 4+5 assertions fail with "missing provider row" — same failure shape as the original bug.

**Why it happens:** GitHub Actions does not warn or error on unresolved step references; missing-step-id silently yields empty.

**How to avoid:** Whichever id slug the planner picks for Step 6, it MUST match exactly between the `outputs.<name>.value` expression and the `id:` field on the step.

**Warning signs:** Scenario 4/5 assertion fails identically to current state, but unit tests pass (because the unit test stubs `setOutput` directly, not the workflow integration).

### Pitfall 3: `setOutput` called with `null`/`undefined`

**What goes wrong:** A future refactor wraps `setOutput` in a conditional that yields undefined for non-dry-run modes. `core.setOutput('dryRunSummary', undefined)` writes the literal string `"undefined"` to GITHUB_OUTPUT.

**Why it happens:** `@actions/core` coerces non-string values via String() before writing the output file.

**How to avoid:** Only call `setOutput` inside `runDryRun` (the dry-run branch). For ingest/heal modes, the output simply remains unset — `${{ steps.run.outputs.dry-run-summary }}` resolves to empty string, which is the correct semantic.

**Warning signs:** A workflow downstream of the action sees `dry-run-summary` literally equal to `"undefined"`.

### Pitfall 4: Forgetting that masking is non-retroactive

**What goes wrong:** Author moves the `::add-mask::` step AFTER `uses: ./`, thinking it will retroactively mask the canary in earlier log lines. It does not. The `with:` header line emitted at `uses: ./` dispatch contains the raw canary; subsequent masking has no effect on already-emitted lines.

**Why it happens:** Aaron Powell's article and `actions/runner` issues #475/#643/#2075 confirm masking applies only to log lines emitted AFTER registration.

**How to avoid:** Place the `::add-mask::` setup step BEFORE the `uses: ./` step in Job A. Verify by inspecting Job A's raw log for ordering — the `Run echo "::add-mask::..."` line must appear before the action's step header.

**Warning signs:** Scenario 1 Job B fails with the same "canary appeared in log" error after the fix.

### Pitfall 5: `outputs:` block placed inside `runs:` instead of at action.yml top level

**What goes wrong:** `outputs:` is misplaced under `runs:` (a common typo). The action.yml parses but the action surface has no outputs.

**Why it happens:** Indentation muscle memory from inputs (which are also top-level) plus outputs being conceptually "produced by runs.steps".

**How to avoid:** `outputs:` is a sibling of `inputs:`, `runs:`, `name:`, `description:` — all top-level keys.

**Warning signs:** YAML parses, action runs, but `${{ steps.run.outputs.dry-run-summary }}` is empty in the consuming workflow.

## Risks / Pitfalls

**Blast radius is small but the regressions are subtle (silent green on red).** Three classes of subtle failure to watch for:

1. **Composite-action output silently empty.** Forgetting `id: run-playwright-healer` on Step 6 produces empty `dry-run-summary` output. Scenarios 4+5 assertions then fail identically to the current state. **Mitigation:** unit test that greps action.yml for both the `id:` field on Step 6 AND the `value:` expression in `outputs.dry-run-summary` — both must be present.

2. **Mask registration order regression.** A future contributor reorders Job A's steps "for clarity" and puts the `::add-mask::` step after `uses: ./`. Masking becomes non-effective on the `with:` header. Job B might still pass if no log line happens to leak the canary that pass — but the test is now structurally broken. **Mitigation:** add a comment block above the Pre-register canary step explicitly stating "MUST precede `uses: ./` — masking is non-retroactive (Pitfall 9 / Phase 01.3 RESEARCH §Pattern 4)".

3. **`runDryRun` test mocks bypass the integration.** Existing unit tests likely mock `@actions/core` directly. A test that asserts `core.setOutput` is called doesn't verify that the composite-action output mapping in action.yml works. The integration is only verified by the live ubuntu-latest run. **Mitigation:** the structural action.yml test (covering `outputs.dry-run-summary.value` + Step 6 `id`) is the integration-side assertion. Combined with the unit test, both halves of the bridge are covered.

- `core.setOutput('dryRunSummary', md)` in production: writes to the per-step `GITHUB_OUTPUT` file. Consumers who don't reference `steps.<id>.outputs.dry-run-summary` see no behaviour change. ✓
- The action.yml `outputs:` block: declarative; no behaviour change unless consumers read it. ✓
- Step 6 `id:` field: cosmetic; no behaviour change. ✓
- Scenario 1 `::add-mask::` setup step: only affects Job A (a self-test job); not part of the published action surface. ✓

**Net production-code change: ONE line in `runDryRun` plus a declarative `outputs:` block. No new threat surface.** The `dryRunSummary` content is the same redacted markdown that already gets written to `core.summary` — already known to be safe to log per Phase 01-06 / 01.1 review.
