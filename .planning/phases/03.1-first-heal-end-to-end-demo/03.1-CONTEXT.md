# Phase 03.1: First Heal — End-to-End Demo

## Why This Phase Exists

Phase 03 shipped 15 plans of healer infrastructure (orchestrator, Gemini adapter
with real `GoogleGenAI` + MCP tool integration, prompt-assembler, fix-applier,
diff-lint, validator, PR-writer, issue-writer, app-supervisor) and reached a
`passed` verification with a "PR was created" HUMAN-UAT marker.

That marker was wrong. There are zero PRs on `Sacharified/playwright-healer-test`.
The five `sc1-healer.yml` runs that did dispatch all failed at a diagnostic
step before the action's heal step ever ran. **The healer pipeline has never
been exercised end-to-end against a real LLM in real CI.**

This phase exists to fix that exactly once. One broken test → one real Gemini
call → one PR with a real fix → fixture-ci.yml on the PR passes. After this
phase, the project will have demonstrated its core value proposition (a flaky
Playwright test results in a reviewable PR without a human reading logs)
exactly one time. Subsequent phases harden the pipeline, broaden fix classes,
add auto-dispatch; but this phase is the "does the concept work at all"
bottleneck gate.

## Goal

A `workflow_dispatch` of `sc1-healer.yml` on `Sacharified/playwright-healer-test`
produces a PR titled `[playwright-healer] Fix flaky <test title>` whose diff,
when applied, makes `fixture/tests/broken-selector.spec.ts` pass. The PR's
own `fixture-ci.yml` workflow run completes with conclusion `success`.

## Locked Decisions (from discuss-phase 2026-04-29)

### D-01: Phase boundary — single bug class, single fixture, single LLM call

Scope is intentionally narrow:
- **One** bug class: selector mismatch (`page.locator('#wrong-id')` where the
  actual element is `#correct-id`)
- **One** fixture test: `fixture/tests/broken-selector.spec.ts` in
  Sacharified/playwright-healer-test (already exists, already broken — verified
  via `gh api` 2026-04-29)
- **One** real LLM call per dispatch: Gemini (per fixture's existing
  `provider: gemini` setting in `sc1-healer.yml`)

Other fix classes (waits, assertions, slow tests), other tests, and other
providers are out of scope. They can come back as Phase 04 / 05 as separate
goals once this demo lands.

### D-02: Validator — keep sanity (step 1), skip post-fix (step 5)

The orchestrator (`src/healer/index.ts`) currently calls `validate()` twice:
- Step 1: pre-LLM sanity check — runs the broken test once to confirm it
  actually fails before burning an LLM call. **KEEP** this; cheap correctness
  gate.
- Step 5: post-fix validation — runs the test N times after applyFix to
  confirm the fix works. **SKIP** for this demo.

The PR's `fixture-ci.yml` is the truth. If the LLM's fix is correct,
fixture-ci.yml passes. If the fix is wrong, fixture-ci.yml fails and we
re-trigger or adjust prompts. Local validator can lie if the runner's
Playwright environment differs from CI; CI is ground truth.

Implementation: simplest path is a `skipPostFixValidation` boolean threaded
through `Config` (or hardcoded `true` for this phase), gating the call at
`src/healer/index.ts:221`. Researcher should look at whether `rerunCount=0`
already short-circuits the validator (might be cheaper).

### D-03: Diff-lint — skip entirely

The orchestrator currently calls `lintDiff(proposal.diff)` at line 195 and
fails the heal if findings are non-empty. **Skip this gate** for the demo.

Rationale: diff-lint is a defense-in-depth guard against `waitForTimeout`,
`:nth-child(`, and weakened assertions. For a one-test selector demo, none
of these patterns apply. If Gemini happens to produce one anyway, that's
information about prompt quality, not an emergency.

Implementation: same shape as D-02 — config flag `skipDiffLint: true` gating
the call. Or simpler: comment out the gate entirely and re-enable in Phase 04
when full fix classes land.

### D-04: Action ref — `uses: Sacharified/playwright-healer@main`

Fixture's `sc1-healer.yml` currently uses `uses: ./`, which requires a
vendored copy of the action source at the fixture repo root. This forces a
sync step on every iteration of the action.

Switch to `uses: Sacharified/playwright-healer@main`. Iteration becomes:
push code to action repo `main` → dispatch `sc1-healer.yml` → watch.

**Known risk:** GitHub Actions cross-repo access between two private repos
requires explicit allowlist (Settings → Actions → "Allow specified actions
and reusable workflows" + entry for `Sacharified/playwright-healer@*`) OR
an org-level setting. If access fails, fall back options:
  - Make `Sacharified/playwright-healer` public (it's intended as an open-source
    action anyway)
  - Keep `uses: ./` and add a one-line fixture-sync step that fetches the
    action source via `actions/checkout` to a sub-path, then `uses: <subpath>`
  - Pin to a release tag (`@v0.1.0-alpha`) instead of `@main`

Investigate during execution; do not block discuss on it.

### D-05: Success criterion — PR opens AND fixture-ci.yml passes on it

Demo is a binary pass/fail:
- ✓ PASS: PR appears with non-empty diff AND `fixture-ci.yml` on the PR has
  conclusion `success`
- ✗ FAIL: anything else (no PR, empty PR, fixture-ci.yml fails)

Up to N attempts allowed (N = whatever's tolerable for one work session,
~5-10 dispatches). Each attempt may surface a different blocker (e.g., MCP
init bug, Gemini auth, prompt produces wrong selector). Each blocker fixed
in turn until the demo lands. The demo is "shipped" when one attempt
satisfies both halves of the success criterion.

### D-06: Cost ceiling for the demo loop

Set `max-budget-usd: 1.00` and `max-turns: 10` in the fixture's
`sc1-healer.yml` `with:` block. These are not strict gates we want to hit;
they're runaway-loop bounds. Single-test selector heals on Gemini 2.5 Pro
should land well under these (a few cents and 3-5 turns). If a single
dispatch hits the budget, the prompt is broken and needs re-tuning.

### D-07: Fixture's broken Debug step — remove entirely

The current `sc1-healer.yml` has a Debug step (`Debug — does Node see
INPUT_HEALER-TOKEN with hyphens?`) that diagnoses G-01 (the npx-tsx env-var
bug). G-01 was closed by Phase 01.2 on 2026-04-27. The Debug step is now
load-bearing on the FAILURE side — it crashes with an unrelated
`ERR_PACKAGE_PATH_NOT_EXPORTED` from tsx's CJS loader on `@actions/core@3.0.1`'s
ESM-only `exports` field.

**Action:** delete the Debug step from `sc1-healer.yml`. It served its purpose;
keeping it now blocks every dispatch.

### D-08: Provider = Gemini (no provider switching for this phase)

The fixture is wired for Gemini (`provider: gemini`,
`api-key: ${{ secrets.GEMINI_API_KEY }}`). Phase 03's adapter implementations
were Gemini-first per CLAUDE.md ("Adapter code lands in Phase 3 under
`src/healer/`, Gemini-first").

Stick with Gemini. Switching to Anthropic introduces a different adapter
code path (manual loop vs Claude Agent SDK) that doubles the surface area
and isn't necessary to demonstrate the concept.

If Gemini consistently fails to produce a correct fix after 5+ tuning
iterations, that's a signal to test Anthropic — but treat that as a follow-up
gap-closure plan, not part of this phase.

## Open Questions for Researcher

These should be resolved during research, not discussed further with the user:

### Q-01: Cross-repo private action access setup

What's the minimal GitHub Actions configuration to let
`Sacharified/playwright-healer-test` invoke
`uses: Sacharified/playwright-healer@main` when both repos are private?
Settings → Actions → "Allow specified actions"? Org-level allowlist?
PAT-based checkout pattern as fallback?

If it requires non-trivial config, the fallback is `actions/checkout` of
`Sacharified/playwright-healer` to a sub-path, then `uses: ./<subpath>`.
That works regardless of repo visibility.

### Q-02: Orchestrator's actual integration shape

The orchestrator (`src/healer/index.ts`) imports a fully wired pipeline,
but it has never been exercised end-to-end against a real LLM. Where are
the integration cracks likely to be?

Hot zones:
  - MCP server spawn: `StdioClientTransport` for `@playwright/mcp` — does it
    boot correctly on the runner?
  - `mcpToTool` integration with `GoogleGenAI` — multi-turn conversation
    state across tool calls?
  - `applyFix` git operations — does the bot author/email + `[skip-healer]`
    sentinel work as advertised?
  - `openHealerPr` PAT permission check — does the PAT have `pull-requests:write`
    on the fixture repo?

Researcher should NOT speculate these failures into being. Just dispatch the
fixture once with the demo config and observe what breaks. Iterate.

### Q-03: Prompt quality for the selector fix class

Current prompts in `src/healer/prompts/` were written without any real LLM
exercise. They may produce diffs that don't compile, don't match the bug,
or use the wrong fix shape (e.g., CSS-attribute selector when the bug is a
typo'd ID). Expect 2-3 prompt iterations.

Researcher should NOT pre-tune prompts. Run the real dispatch first; tune
based on observed Gemini output.

## Scope Guardrail Reminder

This phase has exactly one success criterion (D-05). Anything that doesn't
serve that criterion is out of scope. Resist the urge to "while we're in
here" improve adjacent code. If a code path needs improvement to make the
demo work, change it minimally; if it doesn't, don't touch it.

The discipline here matters: the project has accumulated a lot of
infrastructure ahead of the proof. The lesson is to demo first, harden
later. This phase is the one place that lesson applies — keep it small.
