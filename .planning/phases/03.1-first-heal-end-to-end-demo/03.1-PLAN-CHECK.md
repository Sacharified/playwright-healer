## 5. Structural Issues

### BLOCKER 1: Sentinel validation object crashes pr-writer.ts (Plan 01, Task 1)

Plan 01 Task 1's `<action>` block proposes this pattern when `skipPostFixValidation=true`:

```typescript
const validation = config.skipPostFixValidation
  ? { passed: 0, total: 0, passRate: 1 }  // sentinel — CI is the truth
  : await validate(...);
```

This sentinel object is then passed to `openHealerPr({ validation })`.

`pr-writer.ts:renderPrBody()` accesses `args.validation.perRun.map(...)` (line 32). The
`ValidationResult` type (from `validator.ts`) has `perRun: RunResult[]` as a required field.
The sentinel `{ passed: 0, total: 0, passRate: 1 }` has **no `perRun` field**. At runtime,
`undefined.map(...)` throws a TypeError, crashing the orchestrator before the PR is opened.

This is a concrete crash that blocks the success criterion. The PR will never open.

**Fix required in Plan 01 Task 1:** Change the sentinel to include an empty `perRun` array:

```typescript
const validation = config.skipPostFixValidation
  ? { passed: 0, total: 0, passRate: 1, perRun: [] }  // sentinel — CI is the truth
  : await validate(...);
```

Or alternatively: conditionally call `openHealerPr` with a `validation` only when
`skipPostFixValidation=false`, and make `validation` optional in `OpenHealerPrArgs`. The first
option (add `perRun: []`) is surgical and preferred.

**Also required:** A unit test asserting that when `skipPostFixValidation=true`, `openHealerPr` is
called (not that validate is skipped but PR is still opened). This verifies the sentinel path works.

### BLOCKER 2: Test file path inconsistency — `index.test.ts` location (Plan 01)

RESEARCH's Validation Architecture section says:
```
src/healer/__tests__/index.test.ts
```

Plan 01's `files_modified` frontmatter says:
```
src/healer/index.test.ts
```

The actual codebase has `src/healer/index.test.ts` as a sibling file (no `__tests__/` directory
exists; verified via filesystem). If the executor follows RESEARCH's path, they will create
`src/healer/__tests__/index.test.ts` as a new file while the existing tests remain at
`src/healer/index.test.ts` — Vitest will pick up both, causing duplicate test IDs and
potentially incorrect counts.

**Fix required in Plan 01:** Clarify in both the plan frontmatter and RESEARCH that the target
file is `src/healer/index.test.ts` (sibling). The RESEARCH path reference is stale. Executor
should extend the existing sibling file.

### WARNING 1: TDD task ordering is inverted relative to stated intent (Plan 01)

Plan 01 has:
- Task 1: implementation code (`src/shared/config.ts`, `src/healer/index.ts`, etc.)
- Task 2: tests (`src/healer/index.test.ts`, `src/healer/prompt-assembler.test.ts`)

Task 1's `<done>` says: "Task 2 tests (written first) pass green" — implying Task 2 should run
before Task 1.

Task 2's `<action>` says: "Write TDD-first: write failing tests before touching production code
(then Task 1 makes them green)."

These are internally contradictory within the execution order. An executor following the numbered
task sequence (Task 1, then Task 2) will implement first and test second — the opposite of TDD.

**Fix:** Either swap task numbers (put test task first as Task 1) or add an explicit heading in
Task 1's `<action>` block: "Execute Task 2 (tests) first, then return to this implementation."
Both are adequate. The swap is cleaner.

### WARNING 2: HEALER_TOKEN PAT scope not verified pre-flight (Plan 03)

Plan 03 Task 2 Step D runs:
```bash
gh secret list -R Sacharified/playwright-healer-test
```

This confirms the secret exists (name appears in list) but NOT that it has the required scopes.
The HEALER_TOKEN needs:
- `repo` (for `git push` via the `url.insteadOf` git credential pattern)
- `pull-requests:write` (for `openHealerPr` via Octokit)
- `workflow` scope (for `gh workflow run` dispatch in subsequent iterations)

A PAT with only `read:repo` scope will fail mid-iteration with a 403, which will be harder to
diagnose from action logs than a pre-flight check.

**Fix:** Add a PAT scope verification step to Plan 03 Task 2 or Task 3. Suggested command:
```bash
gh api user -H "Authorization: token $HEALER_TOKEN" | jq '.login'  # confirms token is valid
# For scope check, inspect token scopes header:
curl -s -I -H "Authorization: token $HEALER_TOKEN" https://api.github.com | grep -i "x-oauth-scopes"
```

If `x-oauth-scopes` does not include `repo` and `workflow`, surface to user before dispatching.

### Gap 4 (INFO): No pre-flight that `broken-selector.spec.ts` is still broken on fixture main

Plan 03 Task 4 operates under the assumption that the fixture's broken-selector test is still
present and still failing. If it was inadvertently fixed in the fixture repo (unlikely but possible),
`skipDeterministicCheck=true` bypasses the gate, Gemini calls succeed, but the diff either patches
nothing or makes a no-op change, and fixture-ci.yml runs green on an empty PR.

CONTEXT confirms (D-01): "fixture/tests/broken-selector.spec.ts already broken — verified via
`gh api` 2026-04-29". The verify date is the same day as planning, so this is low risk.

**Mitigation already in plans:** `skipDeterministicCheck=true` bypasses the gate in both
directions — it's fine if the test is broken (expected) or not broken (unexpected edge). If the
fixture test was already fixed, Gemini will produce an empty or wrong diff and fixture-ci.yml will
fail, which is observable.

Not a blocker. Noted for completeness.

### Gap 5 (INFO): Plan 03 Task 2 uses `HEALER_TOKEN` without declaring where the env var comes from

Step D of Plan 03 Task 2 references `$HEALER_TOKEN` in the curl command suggested in WARNING 2
(not currently in the plan). The task's action block doesn't export HEALER_TOKEN to the shell
where `gh secret list` runs — `gh` uses its own auth (from `gh auth login` or `GH_TOKEN`), which
is separate. This is fine for `gh secret list`. However, if the executor adds a PAT scope check
using `curl -H "Authorization: token $HEALER_TOKEN"`, they'll need to source the token from a
local env var or `gh secret get`. This is an execution-time concern, not a plan structure problem.
