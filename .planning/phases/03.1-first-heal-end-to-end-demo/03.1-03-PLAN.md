  <name>Task 2 (Pre-flight): Verify HEALER_TOKEN PAT scopes + fixture-repo secrets exist BEFORE first dispatch (W-2 fix)</name>
  <files></files>
  <action>
    Two pre-flight checks. Both are pure read operations — no destructive ops, no commits.
    Catch the failure modes that otherwise burn 3-5 minutes per dispatch:
    - HEALER_TOKEN missing `repo` or `workflow` scope → mid-dispatch 403 inside the action
    - GEMINI_API_KEY or HEALER_TOKEN missing in fixture repo → action fails at Zod / Gemini auth

    **Step A — Verify HEALER_TOKEN PAT scopes (W-2):**

    Required scopes for `Sacharified/playwright-healer-test` PR creation + downstream CI:
    - `repo` — private repo access; required for `openHealerPr` to push branch + open PR
    - `workflow` — required for the PR's fixture-ci.yml downstream CI to actually fire
      (GitHub's bot-PR recursion guard means PRs opened by GITHUB_TOKEN don't trigger CI;
      the PAT owns the PR, so its scopes determine downstream CI eligibility)

    The HEALER_TOKEN value is in the fixture repo's secrets (not directly readable). What we
    CAN verify is the PAT owned by the local `gh auth` session — assuming the user authenticated
    `gh` with the same PAT they stored as HEALER_TOKEN. If not, surface to user (see fallback).

    ```bash
    # Show scopes attached to the local gh auth token. The "Token scopes" line lists them.
    gh auth status 2>&1 | tee /tmp/gh-auth-status.log

    # Programmatic scope read (X-OAuth-Scopes response header):
    gh api -i /user 2>&1 | grep -i "x-oauth-scopes" || true
    ```

    Inspect the output. The token scopes line should include BOTH `repo` and `workflow`.
    Common substring matches:
    - `repo` may appear as `repo` (full) or as the granular set (`repo:status, public_repo, ...`)
    - `workflow` MUST appear literally — there is no granular alternative

    Decision tree:
    - If both `repo` and `workflow` are present → continue to Step B
    - If `workflow` is absent → STOP. The PAT cannot trigger fixture-ci.yml downstream;
      surface to the user via Task 3 checkpoint with the precise scope deficit
    - If `repo` is absent → STOP. The PAT cannot push branches or open PRs in private repos;
      surface to the user via Task 3 checkpoint
    - If `gh auth status` shows the wrong account (not the one who owns HEALER_TOKEN) → STOP.
      Cannot verify the fixture's secret value from a different account; treat as scope-unverified
      and route to Task 3 checkpoint asking the user to confirm at the PAT-creation page

    **Step B — Verify fixture-repo secrets exist:**
    ```bash
    gh secret list -R Sacharified/playwright-healer-test 2>&1 | tee /tmp/gh-secrets.log
    ```
    Must contain BOTH `GEMINI_API_KEY` and `HEALER_TOKEN`. If either is absent, set
    `SECRETS_MISSING=true` for the next task to route to the human-verify checkpoint.

    Record findings into a temp file the next task reads:
    ```bash
    cat > /tmp/preflight-status.txt <<EOF
    PAT_REPO_SCOPE=$(grep -i "x-oauth-scopes" /tmp/gh-auth-status.log | grep -ic "repo" || echo 0)
    PAT_WORKFLOW_SCOPE=$(grep -i "x-oauth-scopes" /tmp/gh-auth-status.log | grep -ic "workflow" || echo 0)
    SECRET_GEMINI=$(grep -c "GEMINI_API_KEY" /tmp/gh-secrets.log || echo 0)
    SECRET_HEALER=$(grep -c "HEALER_TOKEN" /tmp/gh-secrets.log || echo 0)
    EOF
    cat /tmp/preflight-status.txt
    ```

    **Fail-loud rule:** if any of the four values is 0, do NOT proceed to Task 4 (dispatch).
    Surface the specific deficit to the user via Task 3 checkpoint and wait for confirmation
    that the deficit has been resolved.
  </action>
  <verify>
    <automated>
      # Pre-flight gate: all four checks must show non-zero counts.
