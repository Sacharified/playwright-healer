## Summary

Phase 03.1 exists to run the healer pipeline end-to-end exactly once against a real LLM. The five previous dispatch attempts all failed before the healer code ran — they hit a stale vendored `action.yml` with a diagnostic Debug step that crashes on `@actions/core@3.0.1`'s ESM-only exports. That root cause is now identified. There is zero empirical data about how the current orchestrator code behaves when a real Gemini call is attempted.

Research identified **four blocking integration cracks** that will prevent the demo from succeeding even after the stale vendored action is fixed. The most critical (CRACK-1) is a conflict between D-02 (keep sanity check) and the orchestrator's `passRate === 0` gate: because `broken-selector.spec.ts` is intentionally always-failing, the sanity validate runs it, gets `passRate = 0`, files a `deterministic-failure` issue, and returns — the Gemini adapter is never called. This gate must be bypassed to make the demo work. The three remaining cracks (git push auth, Playwright browser binary, base URL missing in agent context) are also blocking but more straightforward to fix.

Cross-repo private action access (Q-01) has one primary answer: GitHub's per-repo Settings UI lets the action repo share access without any PAT gymnastics.

**Primary recommendation:** Fix all four cracks in one ordered wave of code changes (action code + action.yml + fixture workflow), then dispatch. Expect 2-3 prompt iteration runs after the pipeline first reaches Gemini.

## Q-02: Integration Crack Inventory

All five previous dispatch runs failed at the Debug step. This is CRACK-0 (already diagnosed). The following cracks are what will surface AFTER that is fixed.

### CRACK-0 (Root Cause of All 5 Previous Failures) — Stale Vendored Action

**What goes wrong:** `sc1-healer.yml` uses `uses: ./` which references the vendored copy of `action.yml` at commit SHA `54eeca2b`. That vendored copy has the Debug step that crashes with `ERR_PACKAGE_PATH_NOT_EXPORTED` from `@actions/core@3.0.1`'s ESM-only exports field (Phase 01.2 bug, since fixed in the action repo but not propagated to the vendored copy).

**Fix (D-04 + D-07):** Delete the Debug step from `sc1-healer.yml` AND switch `uses: ./` to `uses: Sacharified/playwright-healer@main`.

**Confidence:** HIGH [VERIFIED: code inspection, CONTEXT acknowledgment]

### CRACK-1 (CRITICAL — Blocks Gemini Call) — Deterministic-Failure Gate Fires on Always-Failing Test

**What goes wrong:** `src/healer/index.ts` Step 4 (line 128-140):

```typescript
const sanity = await validate(payload.testFile, payload.testTitle, config.rerunCount, cwd);
if (sanity.passRate === 0) {
  await fileIssue({ ..., failureMode: 'deterministic-failure', ... });
  return;  // LLM NEVER CALLED
}
```

`broken-selector.spec.ts` is intentionally always-failing (the bug the demo is supposed to fix). `validate()` runs it `rerunCount` times, gets 0 passes, computes `passRate = 0 / rerunCount = 0`. The gate fires, a `deterministic-failure` issue is filed, and the orchestrator returns — Gemini is never called.

**D-02 conflict:** D-02 says "KEEP sanity check" but doesn't address the always-failing fixture scenario. The sanity check as currently written is semantically correct (don't burn LLM on deterministic failures) but logically incompatible with a fixture whose entire purpose is being deterministically broken.

**Fix options (ordered by preference):**

| Option | Change | Risk |
|--------|--------|------|
| Add `skipDeterministicCheck: boolean` flag to Config, gate Step 4 | 3-line config change + 3-line orchestrator change | LOW — surgical |
| Hardcode `rerunCount = 1` in `sc1-healer.yml` and change passRate threshold | misuse of config semantics | MEDIUM |
| Remove the sanity check gate entirely | breaks the invariant for Phase 04+ | HIGH |

**Recommended:** Add `skipDeterministicCheck: true` as a demo-mode flag alongside `skipPostFixValidation` and `skipDiffLint`. All three flags are introduced together in one Config change, gating three orchestrator steps. None of the flags need to appear in `action.yml` inputs — they can be hardcoded `true` for this phase or read from `sc1-healer.yml` inputs.

**Simplest valid implementation:** In `Config`, add `skipDeterministicCheck: z.coerce.string().default('false').transform(v => v === 'true')`. In `sc1-healer.yml`, set `skip-deterministic-check: 'true'`. In the orchestrator, wrap the gate: `if (!config.skipDeterministicCheck && sanity.passRate === 0) { ... }`.

**Confidence:** HIGH [VERIFIED: code inspection of src/healer/index.ts lines 128-140]

### CRACK-2 (HIGH) — Git Push Will Fail with HTTP 401

**What goes wrong:** `action.yml` Step 1 uses `persist-credentials: false` (SEC-01). This removes the runner's auto-configured git credential helper. `fix-applier.ts` calls `git push -u origin branch` at line 97 with no credentials configured. The push fails with HTTP 401/403.

**Fix:** Before the `git push` step, configure HTTPS-based credentials in `action.yml`. Standard pattern from GitHub composite actions:

```bash
git config --global url."https://x-access-token:${HEALER_TOKEN}@github.com/".insteadOf "https://github.com/"
```

This goes in action.yml as a shell step before Step 6 (the main tsx run), using `inputs.healer-token`. The `fix-applier.ts` code needs NO change — it calls `git push` normally and the git config does the credential substitution transparently.

Alternative: pass `token` into `applyFix()` and use `git push https://x-access-token:<token>@github.com/...` directly. This is more invasive (changes the ApplyFixArgs interface).

**Confidence:** HIGH [VERIFIED: code inspection of fix-applier.ts, action.yml SEC-01 pattern]

### CRACK-3 (HIGH) — MCP's Playwright Version Has No Browser Binary

**What goes wrong:** `action.yml` Step 2 runs `npm ci --production` in the action directory. This installs `@playwright/mcp@0.0.70` which declares `playwright@1.60.0-alpha` as a dependency. However, `npm ci --production` does NOT run `playwright install` to download the Chromium binary for that specific playwright version. When the Gemini adapter spawns `npx @playwright/mcp@0.0.70 --headless ...`, the MCP server will fail with:

```
browserType.launch: Executable doesn't exist at /root/.cache/ms-playwright/chromium-NNNNNN/chrome-linux/chrome
```

The fixture's `package.json` uses `@playwright/test@^1.49.1` and its `fixture-ci.yml` runs `npx playwright install --with-deps`. That installs the binary for `^1.49.1`, NOT for `1.60.0-alpha`. The binaries are version-specific; they don't cross-satisfy.

**Fix:** Add a step to `action.yml` after `npm ci --production` to install the Playwright browser for the MCP version:

```yaml
- name: Install Playwright browser (for MCP)
  shell: bash
  working-directory: ${{ github.action_path }}
  run: node_modules/.bin/playwright install chromium --with-deps
```

This runs the playwright CLI from the action's own `node_modules` (which is the `1.60.0-alpha` version), installing into the runner's shared playwright browser cache at the correct subdirectory.

**Confidence:** MEDIUM [ASSUMED based on how Playwright version-specific caches work; not tested on a live runner. The failure mode is well-documented in Playwright MCP issues.]

### CRACK-4 (HIGH) — Base URL Not Passed to Agent

**What goes wrong:** `selectors-no-trace.md` instructs Gemini: "Use the Playwright MCP browser tools to navigate to the application's base URL." But `baseUrl` is:
- NOT included in the `ContextBundle` returned by `context-bundler.ts`
- NOT interpolated into the prompt template by `prompt-assembler.ts` (only `{{TEST_TITLE}}`, `{{TEST_FILE}}`, `{{FORBIDDEN_PATTERNS}}` are interpolated)
- NOT included in `renderContextForAgent()` in `gemini.ts`

The agent will not know what URL to navigate to. It may guess `http://localhost:3000` (the fixture's actual URL) by luck, but that's not guaranteed.

The fixture's `playwright.config.ts` sets `baseURL: 'http://localhost:3000'`, and `sc1-healer.yml` passes `base-url: http://localhost:3000`. The value is available in `config.baseUrl` in the orchestrator. It is also available in `gemini.ts` as `opts.baseUrl` (used for `ALLOWED_ORIGIN_TEMPLATE`). It just isn't passed to the agent's user-facing context.

**Fix options:**

| Option | Change | Intrusion |
|--------|--------|-----------|
| Add `{{BASE_URL}}` to `selectors-no-trace.md`, interpolate in `prompt-assembler.ts` | 2 files changed | LOW — correct |
| Add `baseUrl` to `ContextBundle` and render it in `renderContextForAgent()` | 3 files changed | LOW — also correct |
| Hardcode `http://localhost:3000` in the prompt template | 1 file | HIGH — wrong for non-fixture consumers |

**Recommended:** Add `{{BASE_URL}}` interpolation to `prompt-assembler.ts` and the prompt template. Requires passing `baseUrl` through `AssemblePromptArgs`. This is a 3-line change across 2 files.

**Confidence:** HIGH [VERIFIED: code inspection of selectors-no-trace.md, prompt-assembler.ts, gemini.ts]

### CRACK-5 (MEDIUM — Runtime, Unverified) — StdioClientTransport PATH Inheritance

**What goes wrong (possible):** `StdioClientTransport` for `@modelcontextprotocol/sdk` only inherits 6 env vars from the parent process: `HOME, LOGNAME, PATH, SHELL, TERM, USER`. The MCP subprocess spawned by `gemini.ts` uses `{ command: 'npx', args: ['@playwright/mcp@0.0.70', ...] }` with no `env:` override. If the runner's `PATH` is not inherited correctly, `npx` may not be found.

**Current state:** `StdioClientTransport` does pass `PATH` (it's one of the 6 inherited vars). On GitHub Actions runners, `PATH` is well-set and `npx` is typically on it. This is LOW risk but worth noting.

**Detection signal:** MCP spawn will fail with `ENOENT: npx not found` or similar immediately, before any tool calls.

**Fix (if needed):** Add explicit env override to the `StdioClientTransport` constructor: `env: { ...process.env }`. This is a 1-line change in `gemini.ts`.

**Confidence:** LOW [ASSUMED: based on SDK internals observation; not verified against live runner]

- The selector hierarchy in `selectors-no-trace.md` correctly favors accessible-name selectors over IDs
- The output format is precise and parseable

### What's missing / risky

1. **Base URL absent (CRACK-4):** The agent is told to "navigate to the application's base URL" but the URL is not provided. The agent may hallucinate or refuse. This is the most concrete prompt gap.

2. **No recent error messages:** The orchestrator passes `recentErrorMessages: []` (hardcoded in Step 3). The agent will see `<none provided>`. For this fixture the test source is sufficient (bug is in the locator), but this limits error-guided repair.

4. **Gemini tends to wrap JSON in code fences:** `parseFinalText()` already handles this (`stripped = text.replace(/^\s*```(?:json)?\s*/i, '').replace(/\s*```\s*$/i, '').trim()`). Low risk.

5. **Role-guardrails mention "diff-lint pass":** Step 8 is being skipped (D-03), but the system prompt still says "enforced by a post-fix diff-lint pass". The mismatch is harmless for this demo — the agent doesn't know the diff-lint is skipped and will still produce clean diffs.

### Expected Gemini behavior

For a simple selector typo (`#wrong-id` → `#correct-id`), a capable LLM should:
1. Read the test source, identify `#wrong-id`
2. Navigate to `http://localhost:3000` with the Playwright MCP tool
3. Inspect the DOM for `#correct-id` or similar
4. Propose a 1-line diff changing the locator

The test is maximally simple for this bug class. If the pipeline reaches Gemini cleanly, prompt tuning should require 1-2 iterations at most. The bigger risk is pipeline plumbing (CRACK-1 through CRACK-4), not prompt quality.

## Common Pitfalls

### Pitfall 1: D-02 "Keep Sanity Check" Misread

**What goes wrong:** Reading D-02 as "don't touch the sanity check code" and not adding the bypass flag. The demo dispatches, the sanity check runs the always-failing test, and a `deterministic-failure` issue is opened instead of a PR.

**How to avoid:** D-02's intent is "don't skip the pre-LLM check in production" — but the fixture is a controlled demo where the test is MEANT to be always-failing. The bypass flag satisfies D-02's spirit while enabling the demo. The planner must add `skipDeterministicCheck` as an explicit plan task.

### Pitfall 2: Forgetting the Settings UI Toggle Before Dispatch

**What goes wrong:** `uses: Sacharified/playwright-healer@main` in `sc1-healer.yml` is updated, the commit is pushed, dispatch is triggered, and the job fails immediately with "not authorized to access actions from Sacharified/playwright-healer".

**How to avoid:** The Settings UI toggle on the action repo (`Sacharified/playwright-healer`) must be applied before the first dispatch using the cross-repo ref. This is a human action that cannot be scripted. The planner must include it as a manual step in the plan.

### Pitfall 3: Wrong Playwright Binary Version

**What goes wrong:** `playwright install chromium` is run from the wrong `playwright` binary (e.g., the consumer's `^1.49.1` version instead of the MCP's `1.60.0-alpha` version). The wrong binary version is installed; the MCP still can't launch.

**How to avoid:** Always use `${{ github.action_path }}/node_modules/.bin/playwright install chromium` — this invokes the playwright CLI from the action's own `node_modules`, which matches the version `@playwright/mcp@0.0.70` needs.

### Pitfall 4: rerunCount=0 Doesn't Short-Circuit Sanity Check

**What goes wrong:** Attempting to bypass CRACK-1 by setting `rerun-count: 0` in `sc1-healer.yml`. The validator returns `{ passed: 0, total: 0, passRate: 0 }` (because `total > 0 ? passed / total : 0` returns 0 when total=0). The gate still fires.

**How to avoid:** Use the `skipDeterministicCheck` config flag. Do not try to exploit `rerunCount=0`.

### Pitfall 5: Three Flags Need Input Wiring in action.yml

**What goes wrong:** Config flags are added to `config.ts` but not wired through `action.yml` inputs and env vars in Step 6. The env var `INPUT_SKIP-DETERMINISTIC-CHECK` is never set, Zod reads empty string, transforms to `false`, and the gate still fires.

**How to avoid:** For each new flag: (a) add input in `action.yml` inputs section, (b) add `INPUT_SKIP-*` env var in Step 6's `env:` block, (c) set value in `sc1-healer.yml` `with:` block. All three are required.
