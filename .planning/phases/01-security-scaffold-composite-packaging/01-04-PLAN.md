**Critical non-obvious requirements** (from PATTERNS.md and RESEARCH.md):

  1. **`npm ci --production` MUST be the literal `run:` value of the FIRST composite step** (ROADMAP SC#1 verification: `yq -e '.runs.steps[0].run | test("^npm ci --production$")' action.yml`). Do NOT collapse install + run into a chained shell command (`npm ci --production && npx tsx ...`) — breaks SC#1's "first step" verification AND obscures the failure mode.

  2. **The `env:` block on the `Run playwright-healer` step is LOAD-BEARING** (Pitfall 1). Composite actions do NOT auto-populate `INPUT_*` env vars — `@actions/core.getInput('mode')` returns `""` without this block. All 8 inputs MUST appear. Skipping any one makes that input's Zod validation silently fail at runtime with "got ''".

  3. **`actions/setup-node` MUST be pinned to a commit SHA, NOT `@v6` or `@v6.4.0`** (D-20 + Pitfall 6). The tag-form is a floating reference that can be moved. Use the full 40-char SHA. A comment naming the version (`# v6.4.0`) is allowed (and helpful) but the `uses:` value must be SHA-only.

  4. **`working-directory: ${{ github.action_path }}`** on BOTH `npm ci` step AND `npx tsx` step (PATTERNS item 4). Without this, commands run in the consumer's workspace root and fail to find `package.json` / `src/index.ts`. This is the single most common composite-action deployment bug.

  5. **`shell: bash`** on every `run:` step — required for composite actions (GitHub Actions docs); without it the step fails with "Required property is missing: shell".

  6. **NO `actions/checkout`** step in `action.yml`. The consumer's workflow checks out THEIR repo; `uses: org/playwright-healer@ref` fetches THIS action into the runner at `github.action_path`. Adding a checkout would clone the repo-under-test inside the action, which is wrong. (This also means SEC-01's `persist-credentials: false` check does not find a checkout in this file — Plan 05's lint runs against workflow files AND `action.yml`, so if a future contributor adds a checkout to `action.yml` without `persist-credentials: false`, the lint catches it.)

  7. **NO `runs.using: node20` / `node24`** — must be `composite` (PKG-01). Any other value fails the yq check.

  8. **NO `ncc` / `esbuild` / `dist/` reference anywhere in this file** (D-01 + Pitfall 7).

  9. **NO `pull_request_target`** — not that it would appear in action.yml normally, but the security-lint grep runs against action.yml too; absence is correct.

**About the SHA comment** — a common lint/reviewer request is `# v6.4.0 — verified $(date +%Y-%m-%d)`. Include the `v6.4.0` marker for human readability; do NOT include a mutable timestamp (will cause spurious diffs on re-runs).

**About step names** — use the names above verbatim. The Phase 06 self-test Job B greps for the literal job name "Self-test — mask canary secret"; the action.yml step names don't need to match that (different surface), but consistency aids debugging. Do NOT rename steps without updating downstream references.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Consumer workflow → action.yml | Consumer's inputs flow into the composite via `${{ inputs.* }}`; untrusted values are masked by Plan 03's `core.setSecret` before any log line. |
| action.yml → third-party actions (setup-node) | Supply chain risk if the action tag is moved. SHA-pinning defense. |
| action.yml → action_path/src | The composite runs `npm ci --production` + `npx tsx src/index.ts` against the action's own checked-out tree. Integrity of that tree is enforced by the action's `@ref` pin (consumer's concern, but we document the expectation). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-08 | Tampering (supply chain — floating action tag) | `action.yml` `uses: actions/setup-node@...` | mitigate | Pin to 40-char commit SHA (`48b55a011bda9f5d6aeb4c2d9c7362e8dae4041e` for v6.4.0, re-verified at execution in task 1-04-01). Version comment is human-readable; the `uses:` VALUE is SHA-only. Plan 05's security-lint will ALSO grep all workflow files for floating-tag patterns (future work beyond D-14's 4 checks — noted as open for Phase 2+ extension). |
