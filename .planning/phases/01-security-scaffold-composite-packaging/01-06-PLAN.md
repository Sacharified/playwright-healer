Create `.github/workflows/phase1-self-test.yml` — the end-to-end verification workflow that exercises the composite action against itself.

Purpose:
- This is where ROADMAP SC#3 and SC#4 get mechanically verified. No amount of unit-test-style verification of `src/index.ts` alone (Plan 03) can prove that secret masking works through the Actions runner log pipeline — that requires an actual runner job with the log surfacing behavior.

```yaml
name: Phase 1 Self-Test

on:
  push:
  pull_request:

permissions:
  contents: read
  actions: read          # required by Job B to call gh api on Job A's log

jobs:

  # ──────────────────────────────────────────────────────────────────
  # SCENARIO 1 (SEC-06 / ROADMAP SC#3 / T-1-06) — Canary-mask TWO-JOB pattern.
  #   Job A invokes the action with the inline canary API key.
  #   Job B (needs: A, if: always()) fetches Job A's finalized log via gh api
  #   and asserts the raw canary string does NOT appear.
  # Per PATTERNS Pattern 13, a single-job post-step would race the log API.
  # ──────────────────────────────────────────────────────────────────

  self-test-masking:
    name: 'Self-test — mask canary secret'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd  # v6.0.2 — re-verified at execution
        with:
          persist-credentials: false

      - name: Invoke action with dry-run and inline canary API key
        uses: ./
        with:
          mode: dry-run
          anthropic-api-key: 'test-canary-DO-NOT-USE-REAL-KEY'
          healer-token: 'test-canary-healer-token'
          github-token: ${{ github.token }}

  verify-log-mask:
    name: 'Verify canary was masked in previous job log'
    runs-on: ubuntu-latest
    needs: self-test-masking
    if: always()
    steps:
      - name: Fetch Job A log and assert canary is absent
        env:
          GH_TOKEN: ${{ github.token }}
        shell: bash
        run: |
          set -euo pipefail
          # Locate Job A by its literal job name — MUST match the `name:` on self-test-masking above.
          JOB_ID=$(gh api \
            "repos/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}/jobs" \
            --jq '.jobs[] | select(.name=="Self-test — mask canary secret") | .id')
          if [ -z "$JOB_ID" ]; then
            echo "::error::Could not find job id for self-test-masking"
            echo "--- Available jobs in this run: ---"
            gh api "repos/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}/jobs" --jq '.jobs[] | .name'
            exit 1
          fi
          echo "Job A id: $JOB_ID"
          gh api "repos/${GITHUB_REPOSITORY}/actions/jobs/${JOB_ID}/logs" > job-a.log
          if grep -q 'test-canary-DO-NOT-USE-REAL-KEY' job-a.log; then
            echo "::error::Canary appeared in the log — masking FAILED"
            echo "--- Offending lines: ---"
            grep -n 'test-canary-DO-NOT-USE-REAL-KEY' job-a.log | head -20
            exit 1
          fi
          echo "OK: canary was masked (raw value not found in Job A log)"

  # ──────────────────────────────────────────────────────────────────
  # SCENARIO 2 (CFG-05 / ROADMAP SC#4 / D-06) — Invalid mode fails with Zod error.
  # ──────────────────────────────────────────────────────────────────

  self-test-invalid-mode:
    name: 'Self-test — invalid mode fails fast'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd  # v6.0.2
        with:
          persist-credentials: false

      - name: Invoke with mode=banana (expected to fail)
        id: run
        continue-on-error: true
        uses: ./
        with:
          mode: banana
          anthropic-api-key: 'test-canary-DO-NOT-USE-REAL-KEY'
          healer-token: 'test-canary-healer-token'
          github-token: ${{ github.token }}

      - name: Assert the invocation failed (exit code 1)
        shell: bash
        run: |
          set -euo pipefail
          if [ "${{ steps.run.outcome }}" != "failure" ]; then
            echo "::error::Expected failure for mode=banana, got outcome=${{ steps.run.outcome }}"
            exit 1
          fi
          echo "OK: invalid mode produced failure outcome"

  # ──────────────────────────────────────────────────────────────────
  # SCENARIO 3 (CFG-02 / SC#4) — Missing/empty anthropic-api-key fails cleanly.
  # ──────────────────────────────────────────────────────────────────

  self-test-missing-api-key:
    name: 'Self-test — missing api key fails cleanly'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd  # v6.0.2
        with:
          persist-credentials: false

      - name: Invoke without anthropic-api-key (empty value)
        id: run
        continue-on-error: true
        uses: ./
        with:
          mode: dry-run
          anthropic-api-key: ''
          healer-token: 'test-canary-healer-token'
          github-token: ${{ github.token }}

      - name: Assert failure
        shell: bash
        run: |
          set -euo pipefail
          if [ "${{ steps.run.outcome }}" != "failure" ]; then
            echo "::error::Expected failure for empty anthropic-api-key, got outcome=${{ steps.run.outcome }}"
            exit 1
          fi
          echo "OK: empty api key produced failure outcome"

  # ──────────────────────────────────────────────────────────────────
  # SCENARIO 4 (CFG-05 happy path) — dry-run exits 0 and writes redacted summary.
  # Artifact step also cross-checks the summary file has no canary leak
  # (defense-in-depth on top of Scenario 1's log grep).
  # ──────────────────────────────────────────────────────────────────

  self-test-dry-run:
    name: 'Self-test — dry-run succeeds and redacts secrets in summary'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd  # v6.0.2
        with:
          persist-credentials: false

      - name: Invoke with mode=dry-run and canary api key
        id: run
        uses: ./
        with:
          mode: dry-run
          anthropic-api-key: 'test-canary-DO-NOT-USE-REAL-KEY'
          healer-token: 'test-canary-healer-token'
          github-token: ${{ github.token }}

      - name: Assert success and summary file present without canary leak
        shell: bash
        run: |
          set -euo pipefail
          if [ "${{ steps.run.outcome }}" != "success" ]; then
            echo "::error::Expected success for dry-run, got outcome=${{ steps.run.outcome }}"
            exit 1
          fi
          # $GITHUB_STEP_SUMMARY accumulates across steps in the same job.
          # At this point the previous step populated it.
          if [ -s "$GITHUB_STEP_SUMMARY" ]; then
            if grep -q 'test-canary-DO-NOT-USE-REAL-KEY' "$GITHUB_STEP_SUMMARY"; then
              echo "::error::Canary appeared in \$GITHUB_STEP_SUMMARY — dry-run redaction FAILED"
              exit 1
            fi
            if ! grep -q 'dry-run summary' "$GITHUB_STEP_SUMMARY"; then
              echo "::error::Expected 'dry-run summary' marker in \$GITHUB_STEP_SUMMARY — dispatcher did not write the redacted output"
              exit 1
            fi
          else
            echo "::warning::\$GITHUB_STEP_SUMMARY was empty — cannot confirm redacted dump (non-fatal; Scenario 1 covers masking)"
          fi
          echo "OK: dry-run success + summary redaction verified"
```

**Critical non-obvious requirements** (from PATTERNS items 1-8):

  1. **TWO-JOB pattern is MANDATORY (Pitfall 9)** — a post-step in the same job cannot reliably grep its own log. The Actions log API returns incomplete data until the job exits. Job B's `needs: self-test-masking` + `if: always()` is the only reliable way. A single-job post-step grep would be a phase-failing bug even if it appeared to work in early testing.

  2. **Canary is INLINE literal, NOT `secrets.*`** (Pitfall 8). The string `test-canary-DO-NOT-USE-REAL-KEY` is publicly-documented test data. Using `secrets.TEST_API_KEY` would silently break every contributor's first push (fresh forks lack the secret). The inline literal ensures anyone cloning the repo can run CI without configuring anything.

  3. **`continue-on-error: true` + `steps.run.outcome == 'failure'`** — the action invocation in scenarios 2 and 3 is EXPECTED to fail. `continue-on-error: true` prevents the whole job aborting; then the assertion step checks `outcome == 'failure'`. Without this pattern, scenarios 2/3 would mark the job as failed when the action correctly fails.

  4. **`permissions: actions: read`** — REQUIRED for Job B's `gh api repos/.../actions/jobs/<id>/logs` call. Without it, `gh api` returns 403 and Job B fails with a confusing error.

  5. **Job A's `name:` value MUST match Job B's jq selector VERBATIM**, including the em-dash (—, U+2014). If an editor auto-corrects the em-dash to an ASCII hyphen in one place but not the other, the selector returns empty, `JOB_ID` is blank, and Job B fails with "Could not find job id". Either keep both em-dashes OR replace BOTH with an ASCII hyphen. The reference uses em-dash for readability; acceptance criteria explicitly greps for the match.

  6. **`uses: ./`** — local action reference; resolves to the repo's own `action.yml`. No `@ref` needed. The implicit `actions/checkout` from the outer `steps[0]` makes the repo available at the runner's working directory, and `uses: ./` reads `action.yml` from there.

  7. **`persist-credentials: false`** on every `actions/checkout` step in this workflow (SEC-01 dogfood + Check 2 in Plan 05 enforces it). Four checkouts total (jobs A, C, D, E — Job B has no checkout).

  8. **Healer-token canary** — `'test-canary-healer-token'` — any non-empty string passes the Zod `.min(1)` presence check. Do NOT leave empty (would trigger scenario-3-like failure). Do NOT use `${{ secrets.* }}` for same reason as api-key canary.

  9. **Scenario 4's summary-grep assertion** is defense-in-depth — Scenario 1 proves masking works in the log; Scenario 4 additionally proves the dispatcher's dry-run output itself redacts (per D-05 / Plan 03). If Scenario 1 passes but Scenario 4 fails, it indicates a bug in Plan 03's `runDryRun` helper leaking secrets into the summary markdown.

**What NOT to do:**
  - Do NOT store the canary as a repo secret (Pitfall 8).
  - Do NOT grep the log from within the same job as the run (Pitfall 9 — breaks Scenario 1).
  - Do NOT use `pull_request_target` as a trigger (Plan 05's Check 1 would catch it).
  - Do NOT skip `persist-credentials: false` on any checkout step (Plan 05's Check 2 would catch it).
  - Do NOT use floating tag `@v6` for `actions/checkout` — use SHA.
  - Do NOT rename `self-test-masking` or its `name:` without also updating Job B's `needs:` and the jq selector string.
  - Do NOT add `if:` guards to the assertion steps in scenarios 2/3 — the assertion must run unconditionally to catch the case where the action unexpectedly SUCCEEDS on invalid input.

**About runtime expectations:** Scenarios 2 and 3 trigger `core.setFailed` in `src/index.ts` (Plan 03). Scenario 2's error message includes `mode`; scenario 3's includes `anthropic-api-key` (or `anthropicApiKey` — Zod v4 emits camelCase via `path.join('.')`, per Plan 03 Task 1-03-02 SUMMARY note). The current assertion only checks `outcome == 'failure'` — this satisfies SC#4's "fails fast with a descriptive error". An optional enhancement (not required for Phase 1 sign-off) is to grep for the specific field name in the log; deferred because it would require another two-job log-fetch pattern and Plan 03's Task 1-03-02 already verifies the field-naming locally.
